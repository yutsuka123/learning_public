# セキュア全般ノウハウ：設計から実装まで

[重要] 本書は **IoT プロジェクトで採用しているセキュア技術を、設計判断・仕組み・実装場所・手動実行手順までまとめた統合ガイド** である。  
理由: セキュア技術が複数の文書（`設計概要.md` / `鍵管理および初期セットアップ設計仕様書.md` / `本番セキュア化出荷準備試験計画書.md` / `セキュリティ方針_認証情報取扱い.md` / `LocalServer秘密処理別層仕様書.md` 等）に分散しており、初心者が「なぜこの方式を選んだか」「コードのどこにあるか」を横断的に把握できる文書が不足していたため。

理由: 公開リポジトリ運用のため、漏洩したら被害が大きい情報は本書では「役割」と「保存場所の種類」のみを示す。

[読み方ガイド] 初心者は **§1〜§2 → §3** の順に読むと全体像が掴める。技術詳細を知りたい人は **§4 以降** の各章を必要に応じて参照する。実装場所を素早く知りたい人は **§17 設計書↔実装マッピング** を参照（`013-0002` で別ドキュメント化予定）。

## 1. はじめに：なぜセキュリティが必要か

このシステムは **IoT デバイス（ESP32）が PC やルータ越しにメッセージをやり取りする** 構成。攻撃者がもし入り込めると、以下のような被害が起きる：

| 脅威 | 例 | 本システムでの対策 |
|---|---|---|
| **盗聴** | ネットワーク上の通信を読み取られる | TLS で通信路を暗号化、payload を AES-256-GCM で二重暗号化 |
| **改ざん** | 通信内容を書き換えられる | HMAC-SHA256 で署名、AES-GCM の tag で検証 |
| **なりすまし** | 偽デバイス・偽サーバが接続する | TLS 証明書、MQTT ID/Password、ECDH + 固定公開鍵検証 |
| **物理アクセス** | デバイスを盗まれて中身を解析される | Flash Encryption（ROM 暗号化）、Secure Boot v2、eFuse 封鎖 |
| **PC 複製** | LocalServer のフォルダごとコピーして偽サーバを立てる | DPAPI でユーザー資格情報拘束、`wrapped_secret` は別 PC で復号不可 |
| **改造ファーム** | 攻撃者が改ざんしたファームに差し替える | Secure Boot v2、OTA で署名検証、Rollback で起動失敗時に旧版へ復帰 |

[重要] **完全な防御はない** が、攻撃コストを上げて「楽な経路を塞ぐ」のがセキュリティ設計の現実的なゴール。本書では各対策の **目的と限界** を明示する。

## 2. セキュリティの基本概念（初心者向け）

セキュア技術を理解するための共通用語と分類を先に整理する。

### 2.1 守りたい 4 つの性質（CIA + 認証）

| 性質 | 意味 | 失敗するとどうなる |
|---|---|---|
| **機密性 (Confidentiality)** | 許可された人以外には内容が読めない | 通信や保存データが盗み見られる |
| **完全性 (Integrity)** | 内容が改ざんされていない | 偽の指令が実行される |
| **可用性 (Availability)** | 必要なときに使える | サービス停止 |
| **認証 (Authentication)** | 相手が本物だと確認できる | 偽デバイス・偽サーバに繋がる |
| **否認防止 (Non-repudiation)** | 「やってない」と言えない記録 | 監査で誰がいつ何をしたか追えない |

本システムでは **機密性・完全性・認証** を主軸に設計。可用性は冗長化と AP モード復旧で部分対応。否認防止は監査ログで対応。

### 2.2 暗号の種類

| 種類 | 別名 | 鍵の使い方 | 速度 | 用途 |
|---|---|---|---|---|
| **共通鍵暗号** | 対称暗号 | 暗号化と復号で同じ鍵 | 速い | 大量データの暗号化（payload / Flash） |
| **公開鍵暗号** | 非対称暗号 | 暗号化は公開鍵、復号は秘密鍵（または逆） | 遅い | 鍵交換、署名 |
| **ハッシュ関数** | — | 一方向（戻せない） | 速い | データ指紋（改ざん検知の素材） |
| **MAC** | メッセージ認証コード | 共通鍵で改ざん検知 | 速い | command 署名（HMAC-SHA256） |
| **AEAD** | 認証付き暗号 | 共通鍵で暗号化 + 改ざん検知を同時に | 速い | payload 暗号化（AES-256-GCM） |
| **KDF** | 鍵導出関数 | 元の鍵から目的別の鍵を作る | 速い | k-user / k-device の生成（HKDF / HMAC） |

本システムで採用している主要アルゴリズム：

- **AES-256-GCM**：256 bit 鍵の AEAD。MQTT payload、AP pairing bundle、k-user バックアップで使用
- **HMAC-SHA256**：256 bit ダイジェスト MAC。command 署名、`k-device` 導出で使用
- **HKDF-SHA256**：HMAC を 2 段（extract → expand）して鍵を導出。`k-user` 生成で使用
- **P-256 ECDH**：楕円曲線 Diffie-Hellman。AP pairing 時のセッション鍵交換
- **SHA-256**：ハッシュ関数。`wrapped_secret` 整合性、firmware ハッシュ、salt 計算
- **scrypt**：パスワード派生 KDF。`k-user` バックアップファイルのパスワード保護
- **DPAPI**：Windows OS が提供する暗号化サービス（内部は AES、ユーザー資格情報に拘束）

### 2.3 「鍵」と「秘密値」の違い

- **鍵 (Key)**：暗号アルゴリズムが直接使う値。例：32 byte の AES 鍵
- **秘密値 (Secret)**：鍵の元になるランダム値や、鍵を導出する素材。例：`S_random` は秘密値、そこから派生する `k-user` は鍵

本書では区別して扱う。

## 3. 全体の鍵階層（最重要）

本システムでは **PC 側鍵系統** と **ESP32 製造側鍵系統 (k-iot 系)** の 2 系統がある。

### 3.1 PC 側鍵階層（通常運用のメッセージ保護）

```text
┌─────────────────────────────────────────────────────────────────┐
│ Windows OS のユーザーアカウント（ログイン状態）                     │
│  ┌───────────────────────────────────────────────────────┐      │
│  │ DPAPI（CryptProtectData）                              │      │
│  │  ・ユーザー資格情報に拘束                                 │      │
│  │  ・別 PC や別ユーザーでは復号不可                          │      │
│  └─────────────┬─────────────────────────────────────────┘      │
│                ▼                                                │
│  ┌──────────────────────────────────────┐                       │
│  │ S_random（32 byte CSPRNG）            │                       │
│  │ wrapped_secret.bin として永続化         │                       │
│  └──────────────┬───────────────────────┘                       │
│                 │ HKDF-SHA256                                   │
│                 │ salt = "LocalServer"                          │
│                 │ info = "k-user-v1"                            │
│                 ▼                                                │
│  ┌──────────────────────────────────────┐                       │
│  │ k-user（32 byte、ユーザー環境のルート鍵） │                       │
│  │ メモリ上のみ、ディスク保存禁止              │                       │
│  └──────────────┬───────────────────────┘                       │
│                 │ HMAC-SHA256                                   │
│                 │ message = target_device_name（publicId）        │
│                 ▼                                                │
│  ┌──────────────────────────────────────┐                       │
│  │ k-device（32 byte、デバイス毎の通信鍵）  │                       │
│  │ メモリ上のみ                              │                       │
│  └──────────────┬───────────────────────┘                       │
│                 ├─▶ AES-256-GCM payload 暗号化／復号             │
│                 └─▶ HMAC-SHA256 command 署名／検証              │
└─────────────────────────────────────────────────────────────────┘

別経路：
┌──────────────────────────────────────────────────────────┐
│ k-user-backup.enc.json                                    │
│  ・scrypt(password, salt) → 256 bit 鍵                    │
│  ・AES-256-GCM で k-user を暗号化                          │
│  ・別 PC 復旧用、パスワードと組み合わせて SecretCore で復号  │
└──────────────────────────────────────────────────────────┘
```

### 3.2 ESP32 製造側鍵階層（出荷時のロックダウン）

```text
┌─────────────────────────────────────────────────────────────────┐
│ 工場・製造側で保管（オフライン）                                   │
│  ┌──────────────────────────────────────┐                       │
│  │ k-iot-secure-boot（公開鍵 + 秘密鍵）   │ Secure Boot v2 署名鍵 │
│  └──────────┬───────────────────────────┘                       │
│             ▼                                                    │
│  ┌──────────────────────────────────────┐                       │
│  │ k-iot-flash-encryption（256 bit）     │ Flash Encryption 鍵    │
│  └──────────┬───────────────────────────┘                       │
│             ▼                                                    │
│  ┌──────────────────────────────────────┐                       │
│  │ k-iot-ota-sign（公開鍵 + 秘密鍵）      │ OTA firmware 署名鍵    │
│  └──────────────────────────────────────┘                       │
└─────────────────────────────────────────────────────────────────┘

ESP32 デバイス（不可逆処理後）:
┌─────────────────────────────────────────────────────────────────┐
│ eFuse（1 回だけ書き換え可能なメモリ）                              │
│  ┌──────────────────────────────────────┐                       │
│  │ BLOCK_KEY0: k-iot-flash-encryption    │ → SPI flash 自動暗号化│
│  │ BLOCK_KEY1: k-iot-secure-boot 公開鍵 │ → bootloader が署名検証│
│  │  ダイジェスト                          │                       │
│  │ SECURE_BOOT_EN = 1                    │ → 起動時に署名検証     │
│  │ SPI_BOOT_CRYPT_CNT = 0x1              │ → flash 暗号化を有効  │
│  │ DIS_PAD_JTAG = 1, DIS_USB_JTAG = 1    │ → JTAG 物理経路封鎖   │
│  │ ENABLE_SECURITY_DOWNLOAD = 1          │ → シリアル書込み制限  │
│  └──────────────────────────────────────┘                       │
└─────────────────────────────────────────────────────────────────┘
```

[重要] 当面 **`k-iot-*` は試験用素材を本番でも流用**（鍵新規発行なし、`todo.md` `004-0006`/`004-0007` 退避済み）。本番専用分離は将来対応 `020-0001`。

## 4. PC 側鍵保護：Windows DPAPI

### 4.1 目的

PC を持ち出された場合や、別ユーザーアカウントから `wrapped_secret.bin` を盗まれた場合に、攻撃者が `S_random` を復号できないようにする。

### 4.2 仕組み

**DPAPI (Data Protection API)** は Windows OS が提供する暗号化サービス。

```text
平文（S_random）
     │ CryptProtectData(0, flags=0)
     │  ・内部で Windows ユーザーアカウントの credential を使用
     │  ・現在の Windows ユーザー以外では復号不可
     ▼
wrapped_secret.bin（暗号化済みバイト列）
```

復号は同一 PC・同一 Windows ユーザーで `CryptUnprotectData` を呼ぶと自動的に行われる。

### 4.3 設計判断（なぜ DPAPI？）

| 候補 | メリット | デメリット | 採用 |
|---|---|---|---|
| **TPM 2.0** | ハードウェア拘束、PC ごと盗まれても TPM がないと復号不可 | TPM 非搭載 PC で動作しない、運用複雑 | × |
| **Windows DPAPI** | OS 標準、TPM 不要、ソフトウェアのみで動作 | Windows 限定、ユーザーアカウント侵害時は復号可能 | **○** |
| **暗号化ファイル + パスワード** | OS 非依存、別 PC 復旧可能 | パスワード入力が運用負荷 | バックアップ経路として併用 |
| **macOS Keychain** | Mac OS で同等 | Windows と互換性なし、将来対応 | × (`020-0004`) |
| **Linux libsecret** | Linux で同等 | Windows と互換性なし、将来対応 | × (`020-0004`) |

[判断根拠] 「TPM 必須」だと TPM 非搭載 PC で開発できないため、運用簡素化を優先して DPAPI を採用。バックアップ経路として `k-user-backup.enc.json`（パスワード保護）を併用する二段構え。

### 4.4 実装場所

| ファイル | 行 | 内容 |
|---|---|---|
| `IoT/SecretCore/src/dpapi.rs` | 6-37 | `protect_data` 関数（`CryptProtectData` ラッパ） |
| `IoT/SecretCore/src/dpapi.rs` | 39-70 | `unprotect_data` 関数（`CryptUnprotectData` ラッパ） |
| `IoT/SecretCore/src/key_manager.rs` | 84-115 | `load_or_create_s_random`（CSPRNG 生成 + DPAPI ラップ + `wrapped_secret.bin` 保存・読込） |
| `IoT/SecretCore/src/key_manager.rs` | 229-296 | `WrappedSecretEnvelope`（version / created_at / alg="DPAPI" / payload_base64 / payload_sha256_base64）整合性チェック付き |

### 4.5 コード抜粋（`dpapi.rs:6-37`）

```rust
pub fn protect_data(data: &[u8]) -> Result<Vec<u8>, String> {
    let mut data_in = CRYPTOAPI_BLOB {
        cbData: data.len() as u32,
        pbData: data.as_ptr() as *mut u8,
    };
    let mut data_out = CRYPTOAPI_BLOB { cbData: 0, pbData: ptr::null_mut() };
    let success = unsafe {
        CryptProtectData(
            &mut data_in,
            ptr::null_mut(),  // description
            ptr::null_mut(),  // entropy
            ptr::null_mut(),  // reserved
            ptr::null_mut(),  // prompt
            0,                // flags（0 = 現在ユーザー拘束）
            &mut data_out,
        )
    };
    if success == 0 {
        return Err("CryptProtectData failed".to_string());
    }
    // ... 結果を Vec<u8> へコピーして返す
}
```

### 4.7 限界と注意

- **同一 Windows ユーザーアカウント侵害時は復号可能**：OS にログイン中の攻撃者は DPAPI を呼べる
- **対策**：ユーザーアカウントの権限分離、パスワード強度、Windows Hello 二段階認証など OS レベルの保護を併用

## 5. ESP32 側 ROM 暗号化（Flash Encryption）

### 5.1 目的

ESP32 を物理的に盗まれて SPI フラッシュチップを直接読み取られた場合に、ファームウェアバイナリ・NVS データ・鍵を **読めない状態にする**。

### 5.2 仕組み

ESP32-S3 は **フラッシュ読み書きを SoC 内蔵 AES-256-XTS で自動暗号化**できる。

```text
[CPU] ─────write/read───▶ [SoC 内蔵 Flash Encryption エンジン]
                              │ AES-256-XTS
                              │ 鍵は eFuse BLOCK_KEY0 に焼く
                              ▼
                        [SPI Flash チップ]
                        （暗号化された状態で保存）
```

`SPI_BOOT_CRYPT_CNT = 0x1` の eFuse を焼くと有効化。以後、SPI flash 上のデータは **すべて自動暗号化**される。

ファームウェア書込み時は事前に `espsecure encrypt_flash_data` で **ホスト PC 側で暗号化済みバイナリを作成**してから書込み、または `esptool --encrypt` で書込み時に自動暗号化させる。

### 5.3 設計判断

| 観点 | 判断 |
|---|---|
| **採用するか** | ✅ 採用（第 3 段階セキュア化の一部） |
| **鍵保管** | eFuse `BLOCK_KEY0` に焼き、`RD_DIS`（読出禁止）+ `WR_DIS`（書込禁止）で固定 |
| **書込み方法** | 開発時は `esptool --encrypt`、本番は `espsecure encrypt_flash_data` で事前暗号化 |
| **NVS 暗号化** | **採用しない**（patternA = NVS Encryption なし。理由は §5.6） |

### 5.4 実装場所

| ファイル | 内容 |
|---|---|
| `IoT/ESP32/platformio.ini` | `board_build.embed_txtfiles` / `board_build.partitions = esp32s3_16MB_current.csv` でビルド設定 |
| `IoT/ESP32/partitions/esp32s3_16MB_current.csv` | パーティションテーブル（`app0=0x30000` / `app1=0x430000` / `nvs` / `otadata` / `coredump` / `littlefs`） |
| `IoT/本番セキュア化出荷準備試験計画書.md` §6.4 段階1 | FE 鍵投入・`SPI_BOOT_CRYPT_CNT` 設定・暗号化バイナリ書込み手順 |

### 5.5 手動実行例

```powershell
# 暗号化済みバイナリの生成（ホスト PC 側）
python -m espsecure encrypt_flash_data `
    --keyfile k-iot-flash-encryption.bin `
    --address 0x30000 `
    --output app0_encrypted.bin `
    app0.bin

# eFuse へ Flash Encryption 鍵を焼く（不可逆）
python -m espefuse --port COM4 `
    burn_key BLOCK_KEY0 k-iot-flash-encryption.bin XTS_AES_256_KEY

# SPI_BOOT_CRYPT_CNT を焼く（不可逆、暗号化有効化）
python -m espefuse --port COM4 burn_efuse SPI_BOOT_CRYPT_CNT 0x1

# 暗号化済みバイナリの書込み
python -m esptool --port COM4 write_flash 0x30000 app0_encrypted.bin
```

[厳守] **本番不可逆書込みは `ProductionTool` の段階ランナー経由**で行う（`020-0011` / `020-0012`）。直接 `espefuse` を本番個体に対して実行しない（`020-0012` の二重ゲート `PRODUCTION_TOOL_ENABLE_IRREVERSIBLE_COMMAND_RUNNER=1` + `PRODUCTION_TOOL_ALLOW_IRREVERSIBLE_EXECUTION=1` が必須）。

### 5.6 NVS 暗号化を採用しない理由（案A）

| 観点 | 採用しない判断 |
|---|---|
| **HMAC 鍵 (EF-009b) の eFuse 焼込み** | 本番不可逆対象外 |
| **patternA 運用** | `secureNvsInit.cpp` で「NVS Encryption not enabled in sdkconfig (patternA)」をログ出力 |
| **NVS の保護** | Flash Encryption (SPI 全体暗号化) で間接的に保護される |
| **試験ステータス** | `7041:pipeline:strict=FULL_COMPLETED` で確認済み |

[詳細] `最終セキュア化方式選定メモ.md` §8（案A 詳細）、`問題点記録書.md` #0021。

### 5.7 限界と注意

- **eFuse 鍵が読み出せる場合は終わり**：`RD_DIS` を必ず焼く（`020-0011` 段階1 の最終手順）
- **暗号化前のバイナリが漏れたら意味がない**：オフライン PC で鍵管理（`k-iot-flash-encryption`）
- **書込み中断時の中途半端状態**：`SPI_BOOT_CRYPT_CNT` を焼く前に複数回ビルド・書込み試験を済ませてから不可逆へ進む

- `eFuse適用チェックリスト.md` 段階1

## 6. ESP32 側 Secure Boot v2

### 6.1 目的

ESP32 が起動するときに **ファームウェアが改ざんされていないかを公開鍵検証する**。改ざんされていたら起動を拒否する。

### 6.2 仕組み

```text
電源 ON
   │
   ▼
[ROM ブートローダ]（変更不可、ESP32 内部 ROM 焼込み済み）
   │
   │ eFuse BLOCK_KEY1 から Secure Boot 公開鍵ダイジェストを読む
   │
   ▼
[2nd ブートローダ]（SPI flash 上）の署名を検証
   │
   │ 検証 OK ─▶ [アプリ (app0 or app1)] の署名を検証
   │ 検証 NG ─▶ 起動中止
   │
   ▼
[アプリ]（署名 OK の場合のみ起動）
```

公開鍵 (`k-iot-secure-boot.pub`) のダイジェストは eFuse `BLOCK_KEY1` に焼き、`SECURE_BOOT_EN = 1` で有効化。

ファームウェアビルド時に `espsecure sign_data` で **秘密鍵 (`k-iot-secure-boot.pem`) でアプリと bootloader に署名**する。

### 6.3 設計判断

| 観点 | 判断 |
|---|---|
| **採用するか** | ✅ 採用（第 3 段階セキュア化の必須要素） |
| **バージョン** | Secure Boot v2（v1 は ESP32-S3 では使えない） |
| **署名アルゴリズム** | RSA-PSS 3072 bit（ESP-IDF 既定） |
| **鍵保管** | 秘密鍵はオフライン PC 限定、公開鍵ダイジェストのみ eFuse へ焼く |
| **未使用 slot revoke** | 焼込み後に未使用 SB key slot を revoke して別鍵での署名検証を不可にする |

### 6.4 実装場所

| ファイル | 内容 |
|---|---|
| `IoT/ESP32/platformio.ini` | Secure Boot v2 ビルドフラグ（`CONFIG_SECURE_BOOT=y` / `CONFIG_SECURE_BOOT_V2_ENABLED=y` / 署名鍵パス） |
| `IoT/本番セキュア化出荷準備試験計画書.md` §6.4 段階3 | SB 署名鍵ダイジェスト投入・`SECURE_BOOT_EN`・未使用 slot revoke・`RD_DIS` write-protect の順序 |

### 6.5 手動実行例


## 7. OTA Rollback（旧称「Dual バンク」）

### 7.1 目的

ファームウェア更新時、新版が起動失敗したら **自動的に旧版へ戻す**。これがないと、誤った OTA で全デバイスが文鎮化する。

### 7.2 仕組み

ESP32 のフラッシュには **2 つのアプリ partition** (`app0` と `app1`) が確保されている。これが「Dual バンク」と呼ばれていたもの。

```text
┌─────────────────────────────────────────────────────────────────┐
│ SPI Flash (16 MB)                                                │
│ ┌──────────────────────────────────────────────────────────┐    │
│ │ 0x0000   bootloader                                       │    │
│ │ 0xD000   partition table                                  │    │
│ │ 0xE000   otadata（次回起動する partition を記録）           │    │
│ │ 0xF000   phy_init                                         │    │
│ │ 0x10000  nvs                                              │    │
│ │ 0x30000  app0 (4 MB)  ← 現在動作中                        │    │
│ │ 0x430000 app1 (4 MB)  ← OTA で書込み                      │    │
│ │ 0x830000 coredump                                         │    │
│ │ 0x850000 littlefs (8 MB)                                  │    │
│ └──────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────┘
```

**OTA 動作シーケンス**：

1. 現在 `app0` で起動中
2. OTA で `app1` へ新版ファームウェアを書込み（`esp_ota_*` API）
3. `otadata` を `app1` に切替
4. 再起動
5. **新版で起動 → 動作 OK → `esp_ota_mark_app_valid_cancel_rollback()` を呼ぶ → 確定**
6. **起動失敗 or `mark_app_valid` を呼ばずにタイムアウト → bootloader が自動的に `app0` へ戻す**

これが **Rollback**。

### 7.3 設計判断

| 観点 | 判断 |
|---|---|
| **採用するか** | ✅ 採用（必須機能） |
| **ビルドフラグ** | `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y` |
| **rollback タイムアウト** | アプリ側で `mark_app_valid` を呼ぶまでの自由設計（通常運用では起動後すぐに呼ぶ） |
| **Rollback 試験用モード** | 試験のために `otaRollback.h` で「未確定起動失敗」を意図的に再現できる試験専用 API を用意 |

### 7.4 実装場所

| ファイル | 内容 |
|---|---|
| `IoT/ESP32/platformio.ini` | `build_flags = -DCONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y` / `board_build.partitions = esp32s3_16MB_current.csv` |
| `IoT/ESP32/partitions/esp32s3_16MB_current.csv` | `app0=0x30000` / `app1=0x430000` / `otadata=0xE000` 等 |
| `IoT/ESP32/header/otaRollback.h` | `enableOtaRollbackTestMode` / `disableOtaRollbackTestMode` / `isOtaRollbackTestModeEnabled` |
| `IoT/ESP32/src/otaRollback.cpp` | 試験専用「未確定起動失敗」モード実装 |
| `IoT/ESP32/src/main.cpp:1091` | 試験モード有効時の意図的再起動 |

## 8. TLS 通信

### 8.1 目的

ネットワーク経路上での通信を **盗聴・改ざん・なりすまし** から保護する。

### 8.2 仕組み

TLS (Transport Layer Security) は、TCP の上に **暗号化・認証・整合性検証** をかぶせるプロトコル。

```text
[クライアント]                            [サーバ]
   │ ClientHello                          │
   │  ─────────────────────────────────▶│
   │                                       │ ServerHello + 証明書
   │  ◀─────────────────────────────────│
   │ 証明書検証（CA で署名検証）           │
   │ ECDHE で鍵交換                       │
   │  ─────────────────────────────────▶│
   │                                       │
   │ ハンドシェイク完了、セッション鍵共有     │
   │  ─────────────────────────────────│
   │ 以後、AES-GCM 等で暗号化通信         │
```

### 8.3 設計判断

| 観点 | 判断 |
|---|---|
| **TLS バージョン** | 1.2 以上（1.0 / 1.1 は不可） |
| **暗号スイート** | ECDHE + AES-GCM 系を優先 |
| **証明書配置** | ESP32 側 CA 証明書は `LittleFS` `/certs/` に配置（FW 埋込みから移行） |
| **証明書検証** | サーバ証明書必須、クライアント証明書は将来対応 |
| **MQTT TLS** | 8883 で TLS のみ、`1883` 平文は禁止 |
| **HTTPS OTA** | 4443 で TLS、サーバ証明書必須 |

### 8.4 実装場所

| 通信 | 実装 |
|---|---|
| **MQTT TLS (ESP32)** | `IoT/ESP32/src/MQTT/mqtt.cpp:857-868`（`configureMqttTransportClient` で CA 証明書設定） |

## 10. payload 暗号化（AES-256-GCM）

### 10.1 目的

MQTT payload や AP pairing bundle の **内容を Mosquitto 管理者にも読まれないようにする**（TLS はあくまで経路保護で、Mosquitto 上では平文）。

### 10.2 仕組み

```text
平文 JSON：{"command":"set/relay","state":"on","timestamp":...}
   │
   │ k-device (32 byte) を鍵として AES-256-GCM 暗号化
   │ ・nonce: 12 byte ランダム
   │ ・AAD（任意の関連データ、本システムでは AP bundle で使用）
   │
   ▼
暗号化 payload：
{
  "iv": "<base64 12 byte>",
  "cipher": "<base64 暗号文>",
  "tag": "<base64 16 byte>",
  "mode": "k-device-a256gcm-v1"
}
```

復号時は **tag 検証**が同時に行われるため、**改ざんを検知**できる（AEAD = Authenticated Encryption with Associated Data）。

### 10.3 設計判断

| 観点 | 判断 |
|---|---|
| **鍵長** | 256 bit（128 bit より強い、組込みでも実用速度） |
| **nonce 生成** | 毎回 CSPRNG で 12 byte（再利用厳禁。同じ鍵 + 同じ nonce は致命的） |
| **AAD 採用** | AP pairing bundle で `pairing-secure-bundle-v1|targetDeviceId|sessionId|bundleId|keyVersion` 形式 |
| **入力検証** | key=32 / iv=12 / tag=16 byte 厳格チェック（実装側で例外） |

### 10.4 実装場所（**3 箇所すべて `mbedtls_gcm_auth_decrypt`**）

| ファイル | 行 | 用途 |
|---|---|---|
| `IoT/ESP32/src/maintenanceApServer.cpp` | 881-927 | `decryptAes256GcmForAp`（AP pairing bundle、AAD あり） |
| `IoT/ESP32/src/MQTT/mqtt.cpp` | 604-639 | `decryptAesGcm`（MQTT payload、旧版） |
| `IoT/ESP32/src/MQTT/mqttPayloadSecurity.cpp` | 92-131 | `decryptAesGcm`（MQTT payload security 層、新版・AAD あり） |
| `IoT/SecretCore/src/key_manager.rs` | 488-528 | `encrypt_by_k_device` / `decrypt_by_k_device`（Rust 側、`aes-gcm` クレート） |

### 10.5 コード抜粋（`maintenanceApServer.cpp:902-925`）

```cpp
mbedtls_gcm_context gcmContext;
mbedtls_gcm_init(&gcmContext);
int keyResult = mbedtls_gcm_setkey(&gcmContext, MBEDTLS_CIPHER_ID_AES, keyBytes.data(), 256);
if (keyResult != 0) { /* エラー */ }

int decryptResult = mbedtls_gcm_auth_decrypt(
    &gcmContext,
    plainBytesOut->size(),       // 出力長
    ivBytes.data(), ivBytes.size(),    // nonce
    aadBytes.empty() ? nullptr : aadBytes.data(), aadBytes.size(),  // AAD
    tagBytes.data(), tagBytes.size(),  // tag（検証用）
    cipherBytes.data(),
    plainBytesOut->data()
);
mbedtls_gcm_free(&gcmContext);

if (decryptResult != 0) {
    // tag 検証失敗 = 改ざんあり、または鍵不一致
    return false;
}
```

### 10.6 限界と注意

- **nonce 再利用は致命的**：同じ鍵で同じ nonce を 2 回使うと、過去メッセージとの XOR で平文が判明する場合がある
- **tag 検証を必ず行う**：`mbedtls_gcm_auth_decrypt` は tag 検証付き、`mbedtls_gcm_crypt_and_tag` を復号で使ってはいけない
- **鍵が同じ場合のメッセージ識別性**：暗号化後の payload を見て「同じ送信者」を推測される可能性はある（メタデータ漏洩）

## 12. 鍵導出：HKDF-SHA256 と HMAC-SHA256 直接導出

### 12.1 目的

1 つの根本秘密（`S_random`）から、用途別の独立した鍵を **決定的に再生成可能**な形で導出する。再起動後も同じ秘密から同じ鍵を作れる。

### 12.2 仕組み

#### 12.2.1 HKDF（`k-user` 生成用）

```text
k-user = HKDF-SHA256(
    ikm  = S_random（32 byte）,
    salt = "LocalServer"（アプリ固有識別子）,
    info = "k-user-v1",
    L    = 32 byte
)
```

内部は HMAC を 2 段使う：

1. **Extract**: `prk = HMAC-SHA256(salt, ikm)` で固定長中間鍵を作る
2. **Expand**: `prk` から `info` を組み合わせて目的の長さ（32 byte）まで伸ばす

#### 12.2.2 HMAC-SHA256 直接導出（`k-device` 生成用）

```text
k-device = HMAC-SHA256(
    key     = k-user（32 byte）,
    message = target_device_name（publicId、例: "IoT_04CEF94EB580"）
)
```

出力は HMAC-SHA256 のダイジェスト長そのものの 32 byte。

### 12.3 設計判断（なぜ k-device は HKDF ではなく HMAC 直接？）

| 観点 | 判断 |
|---|---|
| **安全性差** | HKDF も内部で HMAC を 2 段使うため、出力 32 byte の場合の事実上の安全性差はない |
| **実装統一性** | command 署名 (`sign_by_k_device`)、OTA 署名、ESP32 側 `mbedtls_md_*` も HMAC-SHA256 で統一されている。`k-device` 導出だけ HKDF にすると実装が分岐するだけで利点がない |
| **TS 版互換** | 旧 TS 実装で HMAC 直接導出を使っており、互換性維持 |

[歴史] 設計仕様書では当初 HKDF と記述していたが、実装が HMAC 直接導出だった。`todo.md` `009-0012` 精査で正本を実装側へ揃え、設計仕様書 8 件を更新（2026-05-19）。

### 12.5 コード抜粋（`key_manager.rs:137-147` / `454-465`）

```rust
// k-user 生成（HKDF）
pub fn get_k_user(&self) -> [u8; 32] {
    let guard = self.imported_k_user.lock().unwrap();
    if let Some(k_user) = *guard { return k_user; }
    drop(guard);
    let hk = Hkdf::<Sha256>::new(Some(b"LocalServer"), &self.s_random);
    let mut k_user = [0u8; 32];
    hk.expand(b"k-user-v1", &mut k_user).expect("HKDF failed");
    k_user
}

// k-device 生成（HMAC-SHA256 直接導出）
pub fn get_k_device(&self, target_device_name: &str) -> [u8; 32] {
    let k_user = self.get_k_user();
    type HmacSha256 = Hmac<Sha256>;
    let mut direct_hmac = <HmacSha256 as Mac>::new_from_slice(&k_user).unwrap();
    direct_hmac.update(target_device_name.as_bytes());
    let k_dev_result = direct_hmac.finalize().into_bytes();
    let mut k_device = [0u8; 32];
    k_device.copy_from_slice(&k_dev_result);
    k_device
}
```

## 14. eFuse 操作（不可逆処理）

### 14.1 目的

製造工程の最終段階で、**取り外し不可能なロックダウン設定**を ESP32 に焼き付ける。これにより、出荷後はファームウェアを差し替えても改ざんできない状態にする。

### 14.2 仕組み

ESP32 の eFuse は **「1」のビットしか書き込めない、「0」にはもう戻らない**メモリ。一度焼くと永久に取り消せない。

[警告] **eFuse は壊れたら ESP32 全体が文鎮（使用不能）になる**。本番個体への直接実行は厳禁。必ず `ProductionTool` の段階ランナー経由（`020-0011` / `020-0012`）。

### 14.3 段階順序（本番1台目 §6.4）

| 段階 | 内容 | 不可逆 |
|---|---|---|
| **段階1** | Flash Encryption 系：FE 鍵投入（`BLOCK_KEY0`）、`SPI_BOOT_CRYPT_CNT=0x1`、暗号化済みバイナリ書込み | ✅ |
| **段階2** | NVS 暗号化なし確認（案A、非焼込みゲート）：`patternA` ログ、NVS 読書き、AP HTTP 全ロール認証確認 | ❌（焼込みなし） |
| **段階3** | Secure Boot v2 系：SB 署名鍵ダイジェスト投入（`BLOCK_KEY1`）、`SECURE_BOOT_EN=1`、未使用 slot revoke、`RD_DIS` write-protect | ✅ |
| **段階4** | JTAG/DL 封鎖：`DIS_PAD_JTAG`、`DIS_USB_JTAG`、必要時のみ `DIS_USB_SERIAL_JTAG`、最後に `ENABLE_SECURITY_DOWNLOAD` | ✅ |

各段階の **直後** に「読戻し → 再起動 → 4 点証跡確定 → 安定性確認セット（OTA × 2 + AP 10 分 + STA 10 分）」を完了しないと次段階へ進まない。

### 14.4 設計判断

| 観点 | 判断 |
|---|---|
| **NVS Encryption** | 採用しない（案A、patternA） |
| **DIS_USB_SERIAL_JTAG** | 試験中は最後まで保留、最終クローズ時のみ焼く（1 号機ノウハウ）|
| **シリアル出力停止** | eFuse ではなく、量産通常 FW（高詳細ログ抑止版）への OTA で実現 |
| **本番鍵** | 当面試験用と同一、本番専用分離は `020-0001` |

## 15. 機密情報の取扱い方針

### 15.1 絶対に Git に上げないもの

| 種別 | 例 |
|---|---|
| **実パスワード** | `AP_WIFI_PASSWORD`、`AP_ROLE_*_PASSWORD`、MQTT ID/Password |
| **raw 鍵値** | `S_random`、`k-user`、`k-device`、`k-pairing-session`、`k-iot-*` |
| **eFuse 実値** | Flash Encryption 鍵、Secure Boot 公開鍵秘密値 |
| **証明書秘密鍵** | TLS サーバ秘密鍵、OTA 署名秘密鍵 |
| **wrapped_secret.bin の中身** | DPAPI 暗号化済みでも、メタデータが残る可能性 |

### 15.2 サンプルファイル運用

実値はリポジトリに置かず、**`*.sample.txt` / `*Sample.json` を置く**：

| 実ファイル（Git 除外） | サンプル（Git 含む） |
|---|---|
| `IoT/ESP32/data/sensitiveData.json` | `IoT/ESP32/data/sensitiveDataSample.json` |
| `IoT/LocalServer/.env` | `IoT/LocalServer/env.example.sample.txt` |
| `IoT/ProductionTool/.env` | `IoT/ProductionTool/.env.example.sample.txt` |

`.gitignore` で実ファイルを除外、サンプルにダミー値を入れて構造のみ共有。

### 15.3 ログ・コメント・PR

| 場所 | 機密情報の扱い |
|---|---|
| **コード内ログ** | raw 鍵値・パスワード実値を出力しない（`appLogError("decrypt failed")` まで、鍵そのものを出さない） |
| **コードコメント** | 「ここに k-device が入る」までは可、実値・テスト値は書かない |
| **コミットメッセージ / PR** | 機密値を貼らない、Co-Authored-By 等のメタデータのみ |
| **試験記録書.md** | 試験結果は OK/NG のみ、鍵フィンガープリントは先頭 16 桁 hex まで |
| **問題点記録書.md** | スタックトレース等で鍵が混入していないか毎回確認 |

## 16. トラブルシュート観点

セキュア関連で問題が起きたときの一般的な切り分け手順。

### 16.1 MQTT 接続できない

1. **TLS ハンドシェイク失敗**：CA 証明書配置 / 期限 / 名前一致を確認
2. **認証失敗**：mosquitto_passwd の更新、`allow_anonymous false` 設定
3. **ACL 違反**：`acl_file` のトピック設定、user 名一致確認
4. **ポート閉塞**：Mosquitto が `8883` を待受しているか（`netstat -ano | findstr 8883`）
5. **NIC 未接続**：Ethernet/Wi-Fi の物理接続（過去の `#0023` 主因）

### 16.2 OTA 失敗

1. **HTTPS 証明書検証失敗**：LocalServer 側証明書とクライアント側 CA の一致
2. **SHA-256 不一致**：firmware.bin と manifest 内ハッシュの整合性
3. **Secure Boot 署名検証失敗**：`espsecure sign_data` で署名済みか
4. **partition 容量不足**：`app1` の物理容量と firmware サイズ
5. **Rollback 発動**：`mark_app_valid` を呼んでいるか、起動失敗ログ確認

### 16.3 ペアリング失敗

1. **AP モード入れない**：起動時ボタン 3 秒長押しのタイミング、`/api/health` 確認
2. **Wi-Fi 接続失敗（AP）**：`AP_WIFI_PASSWORD` の一致
3. **Web UI ログイン失敗**：4 ロールパスワードの一致
4. **ECDH handshake 失敗**：P-256 公開鍵フォーマット、固定公開鍵検証
5. **bundle 復号失敗**：`k-pairing-session` 鍵不一致 → ECDH 共有秘密の導出に問題

### 16.4 鍵関連

1. **DPAPI 復号失敗**：別 Windows ユーザーで起動していないか
2. **`wrapped_secret.bin` 破損**：`WrappedSecretEnvelope` の整合性メタ（SHA-256）チェック失敗 → `k-user-backup.enc.json` 経路へフォールバック
3. **`k-device` 不一致**：`publicId` の文字列が完全一致しているか（大文字小文字、`IoT_` プレフィックス）
