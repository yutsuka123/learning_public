## 1. システム全体アーキテクチャ

```text
┌─────────────────────────────────────────────────────────────────┐
│  フィールド（デバイス）                                            │
│  ESP32-S3 [C++/FreeRTOS/PlatformIO]                              │
│   └─ WiFi 802.11b/g/n → TLS 1.2 (mbedTLS)                       │
│       ├─ [ローカル] MQTT v3.1.1 → Mosquitto (172.17.1.100:8883)  │
│       └─ [クラウド] MQTT v3.1.1 → AWS IoT Core (X.509 mTLS)     │
└─────────────────────────────────────────────────────────────────┘
              │
┌─────────────────────────────────────────────────────────────────┐
│  PC / ローカルサーバ                                              │
│  LocalServer [TypeScript/Node.js v22]                            │
│   ├─ MQTT.js → subscribe (Mosquitto or AWS IoT Core)             │
│   ├─ Express.js → REST API (HTTP :3100)                          │
│   ├─ ws → WebSocket (リアルタイム UI)                            │
│   ├─ better-sqlite3 → SQLite3 (デバイス履歴)                    │
│   ├─ HTTPS :4443 → OTA バイナリ配信 [ローカル]                   │
│   └─ IPC Named Pipe → SecretCore [Rust]                          │
│       └─ Windows DPAPI → k-device (HMAC-SHA256)                  │
└─────────────────────────────────────────────────────────────────┘
              │
┌─────────────────────────────────────────────────────────────────┐
│  AWS クラウド（ap-northeast-1 東京リージョン）                    │
│  AWS IoT Core (MQTT Broker フルマネージド)                       │
│   └─ IoT Policy (IAM 類似 JSON 認可ポリシー)                    │
│  AWS S3 (ファームウェアバイナリ保管)                              │
│   └─ Presigned URL (時限付き署名 URL → OTA ダウンロード)         │
│  AWS IAM (サービスアカウント・最小権限)                           │
└─────────────────────────────────────────────────────────────────┘
```

## 2. 通信プロトコル

### 2.1 MQTT v3.1.1（Message Queuing Telemetry Transport）[実装済み]

| 項目 | 内容 |
|---|---|
| **用途** | ESP32 ↔ ブローカー間のデバイス制御・状態通知 |
| **ポート** | 8883（TLS 経由） |
| **選定理由** | 軽量・Pub/Sub 非同期・QoS 制御・IoT の事実上標準。ESP32 の限られたリソース（RAM 520KB）でも動作する |
| **バージョン** | v3.1.1（MQTT v5 は AWS IoT Core v1 の制約のため v3.1.1 を採用）|
| **トピック構造** | `esp32lab/<kind>/<sub>/<deviceName>`（例: `esp32lab/notice/status/IoT_04CEF94EB580`）|
| **QoS** | QoS 0（At most once）— デバイス状態通知は欠落より重複を許容しない設計 |
| **実装箇所** | `IoT/ESP32/src/MQTT/mqtt.cpp`（デバイス側）/ `IoT/LocalServer/src/mqttGateway.ts`（サーバー側）|
| **特記事項** | AWS IoT Core では `willRetain=true` は `iot:RetainPublish` 権限が必要。クラウドモードでは `willRetain=false` に固定 |

### 2.2 TLS 1.2（Transport Layer Security）[実装済み]

| 項目 | 内容 |
|---|---|
| **用途** | MQTT 通信路の暗号化（ESP32 ↔ Mosquitto / AWS IoT Core）|
| **ポート** | 8883（MQTT over TLS）|
| **選定理由** | MQTT を平文で流すと MITM 攻撃で通信内容が丸見えになる。TLS は業界標準で ESP32 の mbedTLS に内蔵 |
| **実装方式** | **ローカル**: サーバー証明書認証（CA: 自己署名 `ca.crt`）+ ID/Password / **クラウド**: mTLS（相互認証・X.509 双方向）|
| **証明書 CA** | ローカル: 自己署名 CA（Mosquitto で生成）/ クラウド: Amazon Root CA 1（`AmazonRootCA1.pem`）|
| **ESP32 実装** | mbedTLS（ESP-IDF 内蔵）`IoT/ESP32/src/MQTT/MqttTlsClient.cpp` |
| **LocalServer 実装** | Node.js `tls.connect()` / mqtt.js `tls: true` オプション |

### 2.3 mTLS（Mutual TLS / 相互 TLS 認証）[実装済み - クラウドモード]

| 項目 | 内容 |
|---|---|
| **用途** | AWS IoT Core 接続時の双方向認証。サーバーとクライアント双方が X.509 証明書を提示する |
| **選定理由** | AWS IoT Core は ID/Password を直接サポートしない（Custom Authorizer Lambda が必要になり複雑化）。X.509 は PKI 標準で証明書単位で権限を分離できる |
| **証明書体系** | ESP32 用 cert / LocalServer 用 cert（別証明書・別ポリシーで権限分離）|
| **実装箇所** | `IoT/ESP32/src/MQTT/MqttTlsClient.cpp:setClientAuthContext()` / `IoT/LocalServer/src/cloudMqttSubscriber.ts` |
| **秘密鍵保管** | リポジトリ外（`C:\mydata\project\myproject\certs\`）、Git 除外設定済み |

### 2.4 HTTP / HTTPS [実装済み]

| 項目 | 内容 |
|---|---|
| **HTTP 用途** | LocalServer REST API（:3100）、ESP32 AP モード設定 UI（:80）|
| **HTTPS 用途** | OTA ファームウェア配信（LocalServer :4443 / クラウドモードは S3 presigned URL）|
| **選定理由** | REST API は HTTP で十分。OTA は HTTPS で TLS 検証（改ざんされたバイナリを防ぐ）|
| **HTTPS 証明書** | ローカル OTA: Mosquitto CA 配下の自己署名 / クラウド OTA: Amazon Root CA 1（S3）|
| **ESP32 OTA** | `HTTPClient` + `esp_https_ota`（ESP-IDF）。`IoT/ESP32/src/ota.cpp` |
| **LocalServer** | `express.js` (HTTP) + Node.js `https.createServer()` (HTTPS OTA サーバー)|

### 2.5 WebSocket [実装済み]

| 項目 | 内容 |
|---|---|
| **用途** | LocalServer → ブラウザのリアルタイム状態更新（デバイス一覧のオンライン状態・温湿度が自動更新）|
| **選定理由** | ポーリングは無駄な HTTP リクエストが発生する。WebSocket で push 型にすることで遅延ゼロの双方向通信が実現できる |
| **実装** | Node.js `ws` ライブラリ / `IoT/LocalServer/src/wsGateway.ts` |
| **プロトコル** | `ws://localhost:3100/ws`（同一ホスト内のため HTTP/WS で OK）|

### 2.6 WiFi 802.11 b/g/n（2.4GHz）[実装済み]

| 項目 | 内容 |
|---|---|
| **用途** | ESP32 の無線 LAN 接続（ローカル AP または WAN 接続 AP への接続）|
| **モード** | STA（Station モード / 通常接続）+ AP（Access Point モード / 設定 UI）|
| **認証** | WPA2-PSK / WPA3（AP 依存）|
| **選定理由** | ESP32-S3 に内蔵。2.4GHz は障害物に強く工場・屋内 IoT に適している |
| **2 つの SSID** | ローカルモード: `AP-IoTESP32Test`（閉域 AP・WAN なし）/ クラウドモード: `Buffalo-G-41E0`（WAN 接続 AP）|
| **認証情報保管** | `sensitiveData.json`（LittleFS 上）の `wifi.wifiSSID` / `wifi.wifiPass` |
| **実装箇所** | ESP-IDF `esp_wifi.h` / `IoT/ESP32/src/wifi.cpp` |

### 2.7 Named Pipe（IPC）[実装済み]

| 項目 | 内容 |
|---|---|
| **用途** | LocalServer（TypeScript）↔ SecretCore（Rust）間のプロセス間通信 |
| **選定理由** | TCP ソケットより軽量で OS レベルで保護される（Unix: Unix domain socket / Windows: Named Pipe）。raw k-device を HTTP 等で流さないためのプロセス分離 |
| **プロトコル** | JSON over Named Pipe（`\\\\.\\pipe\\local-server-*`）|
| **実装箇所** | `IoT/LocalServer/src/secretCore.ts` / `IoT/SecretCore/src/main.rs` |

## 3. セキュリティ技術

### 3.1 AES-256-GCM（認証付き暗号）[実装済み]

| 項目 | 内容 |
|---|---|
| **用途** | MQTT payload の暗号化と改ざん検知（ESP32 ↔ LocalServer 間）|
| **選定理由** | AES（共通鍵）は高速でハードウェア実装がある。GCM モードは暗号化と認証を同時に行う AEAD（Authenticated Encryption with Additional Data）。ESP32-S3 は AES ハードウェアアクセラレータを内蔵 |
| **鍵** | `k-device`（デバイス固有の 32 byte 鍵・HMAC-SHA256 で導出）|
| **nonce** | 12 byte ランダム値（毎回再利用なし・リプレイ攻撃防止）|
| **tag** | 16 byte 認証タグ（改ざん検知・タグ不一致で復号拒否）|
| **実装箇所** | ESP32: `IoT/ESP32/src/MQTT/mqttProtocol.cpp` / LocalServer 経由: `IoT/SecretCore/src/crypto.rs` |
| **暗号化スコープ** | AWS IoT Core 上を流れるペイロードも暗号化済み（AWS 側では平文が見えない）|
| **モード** | `MQTT_PAYLOAD_ENCRYPTION_MODE=strict`（全 payload に強制適用）|

### 3.2 HMAC-SHA256（メッセージ認証コード）[実装済み]

| 項目 | 内容 |
|---|---|
| **用途1** | OTA コマンドの署名検証（LocalServer → ESP32 への指令の正当性確認）|
| **用途2** | `k-device` の導出（`HMAC-SHA256(key=k-user, message=publicId)`）|
| **選定理由** | SHA-256 はハッシュ関数として十分な安全性。HMAC は鍵付きハッシュで「改ざん + なりすまし」を同時に防ぐ |
| **OTA 署名フロー** | LocalServer が k-user で署名 → ESP32 が k-device で検証（HMAC-SHA256 は対称なので k-user↔k-device 対応が必要）|
| **実装箇所** | ESP32: `IoT/ESP32/src/ota.cpp:verifyOtaCommandSignature()` / SecretCore: `IoT/SecretCore/src/hmac.rs` |

### 3.3 X.509 PKI（公開鍵基盤）[実装済み]

| 項目 | 内容 |
|---|---|
| **用途** | TLS 接続時のサーバー・クライアント認証 |
| **ローカル PKI** | 自己署名 CA（OpenSSL / Mosquitto で生成）→ Mosquitto サーバー証明書・ESP32 クライアント証明書（現行: ID/Password 認証のため未使用）|
| **クラウド PKI** | Amazon Root CA 1 → AWS IoT Core サーバー証明書 + AWS 発行デバイス証明書 |
| **証明書の役割** | AWS IoT Core は証明書の ARN（Amazon Resource Name）を信頼の根拠とし、IoT Policy で権限を管理する |
| **選定理由** | 公開鍵暗号による認証は共通鍵より安全（秘密鍵が通信路を流れない）。IoT デバイスごとに証明書を発行することで、個別無効化が可能 |
| **実装箇所** | `C:\mydata\project\myproject\certs\`（リポジトリ外保管）/ `IoT/ESP32/data/certs/`（LittleFS 用・Git 除外）|

### 3.4 Windows DPAPI（Data Protection API）[実装済み]

| 項目 | 内容 |
|---|---|
| **用途** | LocalServer が使う `S_random`（秘密の乱数）を OS レベルで保護する |
| **仕組み** | Windows がログインユーザーの資格情報（パスワードハッシュ）で `wrapped_secret` を暗号化・復号する。別 PC・別ユーザーでは復号不可 |
| **選定理由** | TPM 非依存でソフトウェアのみで実現。Windows 標準 API で追加ライブラリ不要。`wrapped_secret.bin` をコピーしても別 PC では復号できない |
| **元の候補** | TPM → ハードウェア依存のため不採用（2026-05-19 方針変更）|
| **実装箇所** | `IoT/SecretCore/src/dpapi.rs`（`CryptProtectData` / `CryptUnprotectData` 呼び出し）|
| **将来対応** | Mac / Linux 汎用化は `020-0004`（Keychain / libsecret への移植）|

### 3.5 Secure Boot v2（ファームウェア署名）[実装済み - デバイス設定]

| 項目 | 内容 |
|---|---|
| **用途** | 不正なファームウェアが起動しないよう、ブートローダーがファームウェアの署名を検証する |
| **仕組み** | eFuse に署名公開鍵のダイジェストを書込み、ブート時に FW バイナリの署名を RSA-PSS で検証。署名が一致しないファームは起動しない |
| **選定理由** | 物理アクセスされたデバイスに改ざん FW を書き込まれても起動させない。Secure Boot v2 は RSA-2048 鍵で複数 slot 管理が可能 |
| **eFuse への書込み** | `ProductionTool` 経由で実施（直接 `espefuse` コマンドの実行は禁止）|
| **実装箇所** | `platformio.ini`（`board_build.embed_files`, `CONFIG_SECURE_BOOT_V2_ENABLED`）/ `IoT/ProductionTool/`（鍵管理）|

### 3.6 Flash Encryption（ROM 暗号化）[実装済み - デバイス設定]

| 項目 | 内容 |
|---|---|
| **用途** | ESP32 のフラッシュメモリ上に保存されたファームウェア・NVS データを読み取り不能にする |
| **仕組み** | ESP32 が初回起動時に AES-XTS 鍵（32 byte）を eFuse 鍵ブロックに書込み、以降フラッシュへの書込み・読み出しをハードウェアで自動的に暗号化・復号する |
| **選定理由** | 物理的にチップを取り外してフラッシュダンプを試みても暗号化されているため解析が困難 |
| **SPI_BOOT_CRYPT_CNT** | eFuse に書込まれる暗号化有効フラグ。一度有効化したら無効化不可（不可逆）|
| **実装箇所** | `platformio.ini`（`CONFIG_FLASH_ENCRYPTION_ENABLED`）/ `ProductionTool` での工場有効化手順 |

### 3.7 eFuse OTP（One-Time Programmable）[実装済み - デバイス設定]

| 項目 | 内容 |
|---|---|
| **用途** | Secure Boot 鍵ダイジェスト・Flash Encryption 鍵・セキュリティフラグの恒久的な書込み |
| **仕組み** | eFuse は一度書込んだら変更不可の OTP メモリ。`SECURE_BOOT_EN` / `DIS_DOWNLOAD_ICACHE` 等のフラグを書き込むことでセキュリティ設定を封鎖する |
| **選定理由** | ソフトウェアで設定を変更できないよう「封鎖」する必要がある。eFuse への書込みは不可逆なので慎重に実施 |
| **実施ツール** | `espefuse.py`（直接実行禁止・`ProductionTool` 経由のみ許可）|

### 3.8 OTA Rollback（デュアルパーティション）[実装済み]

| 項目 | 内容 |
|---|---|
| **正式名称** | `BOOTLOADER_APP_ROLLBACK_ENABLE` / OTA Rollback / app0 + app1 dual partition |
| **用途** | OTA 書込み後に新ファームが正常起動しない場合、自動的に旧ファームへ戻す |
| **仕組み** | `app0`（0x30000）と `app1`（0x430000）の 2 つのアプリパーティションを交互に使用。`esp_ota_mark_app_valid_cancel_rollback()` を呼ばないと次回起動で自動ロールバック |
| **選定理由** | IoT デバイスは OTA 失敗で文鎮化すると回収コストが高い。Rollback で自己回復できる設計が必須 |
| **実施確認** | 試験 7205/7206 で app0→app1→app0 のサイクルを確認済み（v1.1.0-beta.40）|
| **実装箇所** | `IoT/ESP32/src/ota.cpp`（`esp_ota_*` API 使用）/ `platformio.ini`（`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`）|

### 3.9 SHA-256（ハッシュ関数）[実装済み]

| 項目 | 内容 |
|---|---|
| **用途** | OTA ダウンロード完了後のファームウェア整合性検証 |
| **フロー** | S3 アップロード時に SHA-256 ハッシュを計算 → OTA コマンドに含めて ESP32 へ送信 → ESP32 がダウンロード後に SHA-256 を再計算して一致確認 |
| **選定理由** | ダウンロード中のビット化けや MITM による部分改ざんを検知できる |
| **実装箇所** | `IoT/LocalServer/src/server.ts:generateCloudOtaFirmwareUrl()`（計算）/ `IoT/ESP32/src/ota.cpp`（検証）|

### 3.10 鍵導出（HMAC-SHA256 ベース KDF）[実装済み]

| 項目 | 内容 |
|---|---|
| **鍵階層** | `OS 暗号化サービス (DPAPI)` → `S_random` → `k-user` → `k-device` |
| **k-device 導出式** | `HMAC-SHA256(key = k-user, message = publicId)`（publicId = MAC アドレス等のデバイス識別子）|
| **選定理由** | k-device はデバイスごとに異なる鍵でなければならない。k-user から HMAC で導出することで「デバイスごとに固有・k-user なしでは導出不可」を実現 |
| **注意** | HKDF（RFC 5869）ではなく HMAC-SHA256 を直接使用している（2026-05-19 整合済み）|
| **実装箇所** | `IoT/SecretCore/src/key_manager.rs:get_k_device()` |

## 4. ESP32 ファームウェア（C++）

### 4.1 言語・ランタイム

| 技術 | バージョン | 用途 | 選定理由 |
|---|---|---|---|
| **C++17** | ESP-IDF v5.x | ファームウェア全体 | ESP-IDF の公式言語。ARMアーキテクチャで高効率 |
| **FreeRTOS** | ESP-IDF 内蔵 | マルチタスク（MQTT / OTA / AP / センサー取得） | ESP-IDF 標準の RTOS。task / queue / semaphore で並行処理を整理 |
| **ESP-IDF v5.x** | v5.4 相当 | ESP32-S3 向け公式 SDK | PlatformIO と組み合わせてビルド・フラッシュ |
| **PlatformIO** | 最新版 | ビルドシステム・フラッシュ・シリアルモニタ | Arduino IDE より上位の IDE 非依存ビルドシステム。`pio run / pio device monitor` |

### 4.2 ファイルシステム

| 技術 | 用途 | 選定理由 |
|---|---|---|
| **LittleFS** | X.509 証明書・`sensitiveData.json` の永続保存（`/certs/` / `/data/`）| SPIFFS より耐障害性が高い。電源断でもファイルが壊れにくい |
| **NVS（Non-Volatile Storage）** | k-device・WiFi SSID/Pass・brokerMode 等の key-value 保存 | 書き換え回数に強い（フラッシュウェアレベリング内蔵）。Flash Encryption 時に NVS 区画ごと暗号化される |

### 4.3 デバイス固有機能

| 技術 | 用途 | 備考 |
|---|---|---|
| **AP モード（SoftAP）** | BOOT ボタン長押しで設定 UI を起動。WiFi SSID/Pass・brokerMode を変更 | `IoT/ESP32/src/maintenanceApServer.cpp` |
| **OTA（Over-The-Air Update）** | ファームウェアの無線更新（ローカル HTTPS / クラウド S3）| `esp_https_ota` / `IoT/ESP32/src/ota.cpp` |
| **シリアルモニタ** | デバッグ出力（UART 115200 bps）| `pio device monitor` |
| **ArduinoJson** | `sensitiveData.json` の JSON シリアライズ・パース | ESP32 向けに最適化された JSON ライブラリ |

### 11.2 設計上の工夫・アピールポイント

#### セキュリティ設計
1. **多層防御**: TLS（通信路）+ AES-256-GCM（payload 二重暗号化）+ X.509 認証の組み合わせ
2. **ゼロ知識設計**: AWS IoT Core 上では payload は暗号化されたまま。クラウド側で平文データを見ることはできない
3. **最小権限原則**: IoT Policy でデバイス・サーバー別に publish/subscribe トピックを個別に制限
4. **鍵の階層化**: DPAPI → S_random → k-user → k-device と階層化することで k-device が漏洩しても上位鍵は安全
5. **OTA 安全性**: SHA-256 検証 + HMAC 署名 + OTA Rollback で「ダウンロード失敗・改ざん・起動失敗」を多層防御

#### クラウド・ローカルハイブリッド設計
1. **フォールバック設計**: `CLOUD_MQTT_ENABLED=false` / `brokerMode=local` に変更するだけで 2 分以内にローカルモードへ復帰
2. **既存コードへの影響ゼロ**: クラウド対応を追加しても LocalServer / ESP32 のローカルロジックは一切変更なし
3. **コスト管理**: 試験時のみクラウドモードに切替え。常時接続でも AWS 無料枠（12ヶ月 500K msg/月）内に収まる試算

#### OTA 設計
1. **クラウド OTA のアーキテクチャ**: ESP32 と LocalServer が異なるネットワーク（WAN 越し）にある場合でも、LocalServer は S3 に upload → Presigned URL を生成 → AWS IoT Core 経由でコマンドを ESP32 へ送信 → ESP32 は S3 から直接 HTTPS ダウンロード。LocalServer を OTA バイナリの中継役にしないため、ファイルサイズ制限の影響を受けない
2. **デュアルパーティション**: app0 / app1 を交互に使い、OTA 失敗時に自動ロールバック
3. **不正 OTA 防止**: HMAC 署名検証 + SHA-256 整合性チェックの組み合わせ
