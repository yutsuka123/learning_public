# 鍵管理・初期セットアップ 実装たたき台

[重要] 本書は `鍵管理および初期セットアップ設計仕様書.md` を実装へ落とし込むためのドラフトである。  
理由: `OS 暗号化サービス（現行: Windows DPAPI、ソフトウェア暗号化・チップ非依存） + wrapped_secret + HKDF` 方式の実装順序と責務分担を先に固定し、手戻りを防ぐため。Mac/Linux 汎用化は `020-0004`。

[厳守] 本書には鍵実値・秘密情報を記載しない。  
理由: 公開リポジトリ運用のため。

## 1. スコープ（第1版）
- 対象:
  - `S_random` 生成
  - OS 暗号化サービス（現行: Windows DPAPI）による `wrapped_secret` 生成・保存
  - `wrapped_secret` 復号による `k-user` 再生成
  - `k-device` 導出
  - `createPairingBundle` 生成
  - Wi-Fi更新での暗号 payload 生成/受信準備
  - 同一PC再インストール時の `wrapped_secret` / `device_db` 復元
- 対象外（次版）:
  - macOS / Linux 向け同等ソフトウェア暗号化への汎用化（→ **`020-0004`**）
  - クラウドKMS連携
- [改訂][2026-05-19] 旧 TPM 前提は撤回。実装は最初から Windows DPAPI（`SecretCore/src/dpapi.rs` / `SecretCore/src/key_manager.rs`、`WRAPPED_SECRET_ALG="DPAPI"`）であり、設計仕様書もこれに合わせて更新済み（`鍵管理および初期セットアップ設計仕様書.md` §2 / §16）。

## 1.1 責任範囲の親定義
- [厳守] `ProductionTool` / `LocalServer` / `SecretCore` / `ESP32` の責任境界は `モジュール仕様書.md` を親定義とする。
- [厳守] 本書はそのうち `LocalServer` と `SecretCore` の実装たたき台を主対象とし、`ProductionTool` の eFuse 実行主体を混在させない。

## 1.2 高リスクワークフロー方針
- [厳守] TS は高リスク処理の開始要求、入力検証、進捗表示、結果表示のみを担当する。
- [厳守] `SecretCore` は対ESP32通信開始から完了判定までを Rust 主導ワークフローとして実行する。
- [厳守] ワークフロー名は `runPairingSession()`、`runKeyRotationSession()`、`runProductionSecureFlow()`、`runSignedOtaCommand()` を基本とする。
- [厳守] 進捗状態は `queued` / `running` / `waiting_device` / `verifying` / `completed` / `failed` を正規値とする。

## 2. 実装フェーズ案
[厳守][2026-05-19] Phase1〜4 の「担当」は **責任モジュール** で表記し、「期限」は **相対順序**（依存関係ベース）で表記する。  
理由: 単独運用前提で空振りの絶対日付を作らず、`009-0008` の運用ルールとして固定するため。出典: `todo.md` `009-0008`（2026-05-19 着手）。

### Phase 1: OS 暗号化サービス初期化基盤
- 担当: `SecretCore`（主：`S_random` 生成・OS 暗号化サービス（現行: DPAPI）ラップ・`wrapped_secret` 配置） / `LocalServer`（起動時呼出・初期化判定）
- 期限: `009-0009`（Phase1 最小実装）着手の前提として確定させる。Phase2〜4 はこれが揃ってから着手する。
- [現状][2026-05-19] **実装済み**。`SecretCore/src/key_manager.rs:84-115 load_or_create_s_random()` で CSPRNG 生成 → `dpapi::protect_data` → `wrapped_secret.bin` 保存まで動作。`機能仕様書.md` F3-091 に明文化済み。
- セットアップ処理で `S_random` を CSPRNG 生成する（32 byte、`rand::rng().fill_bytes`）。
- OS 暗号化サービス（現行: Windows DPAPI `CryptProtectData`）で `S_random` をラップし、`wrapped_secret` を保存する。
- `wrapped_secret` 保存先（`LocalServer/data/wrapped_secret.bin`）と ACL を固定する。
- 失敗時エラー設計:
  - OS 暗号化サービス呼出し失敗（DPAPI: `CryptProtectData failed`）
  - 保存先権限不足
  - 既存 `wrapped_secret` との競合
  - `WrappedSecretEnvelope` 整合性チェック失敗（version / created_at / SHA-256）

### Phase 2: LocalServer 起動時鍵導出
- 担当: `SecretCore`（主：`load_or_create_s_random` / `get_k_user` / `get_k_device`） / `LocalServer`（起動時に `SecretCore` を呼び、運用者向け状態のみ取得）
- 期限: Phase1 完了後に着手。`009-0012`（サーバ側 `k-device` 導出処理実装）は実装済みとして退避済み（`todo_old20260519.md`）。
- [現状][2026-05-19] **実装済み**。`SecretCore/src/key_manager.rs:137-147 get_k_user()` で HKDF 導出、`:454-465 get_k_device()` で `HMAC-SHA256(key=k-user, message=target_device_name)` 導出が完了。`target_device_name` は `publicId`（例: `IoT_04CEF94EB580`）。旧 HKDF 式（`HKDF(ikm=k-user, salt=SHA256(base_mac), info="k-device-v1")`）は 2026-05-19 撤回。理由は `鍵管理および初期セットアップ設計仕様書.md` §6.2 / §16 参照。`009-0012` は実装済みとして完了退避済み。
- `wrapped_secret` を読込む。
- OS 暗号化サービス（現行: DPAPI `CryptUnprotectData`）で `S_random` を復号する。
- HKDF で `k-user` を生成する。
- `device_id`（base MAC）から `k-device` を導出する。
- `k-user` / `k-device` はメモリ上のみ保持し、使用後はゼロ化する。

### Phase 3: 初回ペアリング・暗号通信
- 担当: `SecretCore`（主：`runPairingSession()` と内部 `createPairingBundle`） / `LocalServer`（入力検証・REST `/api/workflows/pairing/start`・進行表示） / `ESP32`（APモード受入・bundle 検証・`k-device` 利用）
- 期限: Phase2 完了後に着手。`009-0010`（Phase2 UI/CLI 手順確定）／`009-0014`（MQTT トピック統一）／`009-0017`（ESP32 AES-256-GCM 復号）／`009-0018`（初回ペアリング AP モード実装）と並走して進める。
- デバイスAPモード起動（物理操作必須）
- `LocalServer` で必須入力（Wi-Fi / MQTT / OTA / 認証情報）を事前検証
- `SecretCore` で `runPairingSession()` を開始
- `createPairingBundle` は workflow 内部で生成
- AP モード ECDH と固定公開鍵検証前提で bundle を投入し、完了判定まで実行
- MQTT / OTA / Wi-Fi設定更新で `k-device` を利用

### Phase 4: バックアップ/復元
- 担当: `LocalServer`（主：`backup-manager` モジュール・`exportWrappedSecretBackup` / `exportDeviceDbBackup` / `restore*Backup` REST 公開） / `SecretCore`（OS 復号確認・整合性検証）
- 期限: Phase3 で `k-device` 経由の通信が成立した後に着手。`008-0030`（バックアップ導線）退避済みの土台を流用し、`同一PC再インストール復旧試験`（`9. 先行実装順` の 8 番）で閉じる。
- `wrapped_secret` と `device_db` をバックアップ対象とする。
- 再インストール時に両ファイルを復元する。
- 同一PC + 同一 OS ユーザー資格情報（現行 DPAPI: 同一 Windows ユーザー）でのみ復旧できることを確認する。
- [禁止] 平文 `k-user` をバックアップ対象にしない。

### Phase 5: 障害時運用
- 担当: `LocalServer`（再登録フロー UI / API） / `SecretCore`（鍵再発行と `wrapped_secret` 再生成）
- 期限: Phase4 完了後の将来対応。`008-0031` 完了退避（2026-05-14）で UI 受け皿は整備済みのため、本書では運用観点のみ追跡する。
- DPAPI マスター鍵消失時（Windows ユーザープロファイル再作成等）の再発行フロー
- マザーボード交換時の再登録フロー
- PC故障時の全デバイス再登録フロー

## 3. モジュール案（PC側）
- `setup-core`:
  - `S_random` 生成、OS 暗号化サービス（現行: DPAPI）によるラップ、`wrapped_secret` 配置
- `secret-core`:
  - OS 暗号化サービス（現行: DPAPI）復号、`k-user` 生成、`k-device` 導出、署名/HMAC、workflow 実行、監査ログ
- `device-registry`:
  - `device_db` 管理、`base_mac` / `public_id` / 状態情報保持
- `local-server-ui`:
  - AP 共通トップ画面、入力検証、進行状態表示、監査表示
- `backup-manager`:
  - `wrapped_secret` / `device_db` のエクスポート・インポート
- `support-package`:
  - 鍵を含まない診断情報パッケージ生成

## 4. モジュール案（ESP側）

  - `device_id` 取扱い、受信メッセージ検証
- `filesystem.cpp`:
  - NVS / LittleFS 保存処理
- `wifi.cpp`:
  - APモード/通常モード切替
- `mqtt.cpp`:

## 6. APIたたき台
### 6.1 セットアップ API（PC内）
- `initializeKeyHierarchy() -> { created: boolean, keySchemaVersion: string }`（実装: `KeyManager::new` 内で `load_or_create_s_random` を呼ぶ）
- `isKeyHierarchyInitialized() -> boolean`（実装: `wrapped_secret.bin` の存在確認）
- `rewrapSecret() -> { rotated: boolean }`（将来対応・`020-0004` 検討対象）

### 6.2 SecretCore API
- `unwrapSecretToRuntime() -> boolean`（実装: `load_or_create_s_random` 内の `dpapi::unprotect_data` 経路）
- `deriveUserKey() -> runtimeOnly`（実装: `get_k_user` の HKDF）
- `deriveDeviceKey(baseMac: string) -> runtimeOnly`
- `runPairingSession(targetDeviceId, sessionId, keyVersion, requestedSettings) -> { workflowId, state }`
- `runKeyRotationSession(targetDeviceId, sessionId, keyVersion, requestedSettings) -> { workflowId, state }`
- `runProductionSecureFlow(deviceId, runId, productionSettings) -> { workflowId, state }`
- `runSignedOtaCommand(targetDeviceId, firmwareVersion, manifestUrl, firmwareUrl, sha256) -> { workflowId, state }`
- `getWorkflowStatus(workflowId) -> { state, result, errorSummary }`
- [厳守] `createPairingBundle(...)` は `runPairingSession()` 内部 helper とし、`LocalServer` 公開 API にしない。

### 6.3 LocalServer REST API
- `POST /api/workflows/pairing/start -> runPairingSession(...)`
- `POST /api/workflows/key-rotation/start -> runKeyRotationSession(...)`
- `POST /api/workflows/production/start -> runProductionSecureFlow(...)`
- `POST /api/workflows/signed-ota/start -> runSignedOtaCommand(...)`
- `GET /api/workflows/{workflowId} -> getWorkflowStatus(...)`
- [厳守] REST 応答は `workflowId`、`state`、`result`、`errorSummary` に限定し、raw key や中間秘密を返さない。
- [禁止] `POST /api/pairing/bundle` のような内部 helper 直公開 API を作成しない。

### 6.4 バックアップ API
- `exportWrappedSecretBackup() -> file`
- `exportDeviceDbBackup() -> file`
- `restoreWrappedSecretBackup(file) -> boolean`
- `restoreDeviceDbBackup(file) -> boolean`

## 7. 試験観点たたき台
- 鍵生成:
  - `S_random` が毎回異なること
  - `wrapped_secret` だけが保存され、平文秘密が残らないこと
- 起動時導出:
  - 同一PCで `k-user` が再現できること
  - `k-device` が同一 `base_mac` から再現できること
- workflow 実行:
  - `runPairingSession()` が必須設定不足で前段検証停止すること
  - `runKeyRotationSession()` が個体単位で完了判定できること
  - `runProductionSecureFlow()` が段階実行と再判定を扱えること
  - `runSignedOtaCommand()` が署名付き開始指示と完了判定を扱えること
  - raw `k-device` や `k-pairing-session` が TS 側へ返らないこと
  - 進捗状態が `queued` / `running` / `waiting_device` / `verifying` / `completed` / `failed` で遷移すること
- 別PC移行防止:
  - `wrapped_secret` 単体を別PC（または同一 PC の別 Windows ユーザー）へコピーしても復号失敗すること
- 再インストール復旧:
  - 同一PCで `wrapped_secret` + `device_db` 復元後に通信継続できること
  - 別PCで `k-user-backup.enc` + パスワード + `device_db` 復元後に通信継続できること
- 障害時:
  - DPAPI マスター鍵消失（Windows ユーザープロファイル再作成等）後は既存 `wrapped_secret` を復号できないこと
  - `k-user-backup.enc` 経路で復旧できること
  - 復旧不能時は再発行後に再登録が必要になること

## 8. リスクと対策たたき台
- リスク: Windows DPAPI が利用できない環境（Mac / Linux）で動作しない
  - 対策: 現行は Windows のみサポート。Mac / Linux 汎用化は **`020-0004`** で Keychain Services / libsecret 等への抽象化を検討する
- リスク: `wrapped_secret` 破損で復旧不能
  - 対策: `WrappedSecretEnvelope` の整合性チェック（`SecretCore/src/key_manager.rs:288-294`）に加え、`k-user-backup.enc` による復旧経路を併用し、バックアップ運用を導入手順書へ追記する
- リスク: 同一PC侵害時のメモリ窃取
  - 対策: `k-user` / `k-device` 保持時間最短化、zeroize、監査ログ強化
- リスク: Windows ユーザーアカウント侵害時の DPAPI 復号
  - 対策: ユーザーアカウントの権限分離・パスワード強度を導入手順書へ明記し、`k-user-backup.enc` 経路は別パスワード保護とする
- リスク: device DB 欠損
  - 対策: `device_db` のバックアップ必須化と整合性チェック実装

## 9. 先行実装順（提案）
1. `secret-core` に OS 暗号化サービス（現行: Windows DPAPI）初期化と `wrapped_secret` 生成を実装する（**実装済み**: `SecretCore/src/key_manager.rs:84-115 load_or_create_s_random()` / `SecretCore/src/dpapi.rs`）  
2. LocalServer 起動時の `wrapped_secret` 読込 + `k-user` 導出を実装する  
3. `deriveDeviceKey(baseMac)` を実装する  
4. `device_db` と `public_id` の管理を実装する  
5. `runPairingSession()` を実装する  
6. `runSignedOtaCommand()` を実装する  
7. `runKeyRotationSession()` / `runProductionSecureFlow()` を実装する  
8. 同一PC再インストール復旧試験を実施する
