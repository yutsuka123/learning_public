## 記録 #0001
- 見出し: ESP32からMQTT(1883)へ到達できない
- 種類: コマンド
- 分野: サーバー
- 状態: 解決済
- 試験番号: 7001
- 日時: 2026-03-02

### 症状
- ESP32 側ログで `WiFiClient connect timeout 3000 ms` が継続し、`kMqttInitDone` を受信できない。

### 原因
- ブローカPCのWi-Fiネットワークプロファイルが `Public` だったが、FWルール `mqtt` は `Private` のみ適用だった。
- その結果、同一LAN内のESP32から `172.16.1.59:1883` への受信許可が適用されなかった。

### 対策
- ブローカPCのFW適用プロファイルを実ネットワーク条件に合わせる（Public/Private整合）。
- 必要に応じて MQTT受信ルールを Public へも適用。
- 接続検証時にネットワークプロファイル種別を初期確認項目へ追加。

### 再発防止
- [厳守] `運用記録_ESP32_MQTT接続検証_2026-03-02.md` の「重要な注意点」を接続試験前チェックとして運用する。
- [推奨] 将来は IoT専用LAN を `Private` とし、ルールをサブネット限定する。

## 記録 #0002
- 見出し: ESP32のみMQTT over TLS証明書検証に失敗する（-9984）
- 種類: デバッグ
- 分野: サーバー
- 状態: 解決済
- 試験番号: 7002
- 日時: 2026-03-06

### 症状
- ESP32ログで `(-9984) X509 - Certificate verification failed` が継続し、MQTT初期化が完了しない。
- 一方でPC側クライアント（`mosquitto_pub/sub`、`mqtt.fx`）は同一Brokerへ接続できる。

### 原因
- DNS名運用時は `mqttUrl=<パソコン名>` をESP32側で解決できず、`DNS Failed` が発生した。
- `mqttUrl=172.16.1.59` へ変更後も、ESP32（Arduino-ESP32 / mbedTLS）で証明書照合条件が厳密に一致せず、証明書検証エラーが発生した。

### 対策
- サーバ証明書のSANを以下構成へ調整して再発行した。
  - `IP:172.16.1.59`
  - `DNS:172.16.1.59`
  - `DNS:CF-FV_1`（任意）
  - `DNS:localhost`（任意）
- ESP32接続先は `SENSITIVE_MQTT_URL="172.16.1.59"` を維持し、DNS依存を回避した。
- CA証明書(`ca.crt`)をESP32の `SENSITIVE_MQTT_TLS_CA_CERT` に同期反映した。

### 再発防止
- [厳守] 接続試験時は `mosquitto_pub/sub` とESP32ログを同時確認し、DNS・証明書・認証の失敗層を分離して判定する。
- [推奨] SANは `IP` と `DNS` の両方を登録し、クライアント実装差異の影響を避ける。

## 記録 #0003
- 見出し: ESP32 から LocalServer OTA HTTPS(4443) へ接続できない
- 種類: デバッグ
- 分野: サーバー
- 状態: 解決済
- 試験番号: 7010
- 日時: 2026-03-07

### 症状
- `POST /api/commands/ota` に対して ESP32 は `ota start queued` を受信し、`esp32lab/notice/otaProgress/<device>` へ `prepare / retry / error` を publish する。
- しかし OTA 本体では `HTTPClient connect(): failed connect to mqtt.esplab.home.arpa:4443` および `returnError(): error(-1): connection refused` が出力され、更新処理へ進めない。

### 原因
- PC側 `LocalServer` では `OTA HTTPS started. httpsPort=4443` を確認しており、同一PCからの `curl -k https://127.0.0.1:4443/ota/manifest.json` / `firmware.bin` は取得できる。
- `Test-NetConnection -ComputerName 172.16.1.59 -Port 4443` は PC上で成功しているため、LocalServer の待受自体は成立している。
- Windows 側 `4443/TCP` 許可後の再試行でも、ESP32 では引き続き `connection refused` が再現した。
- 追加切り分けの結果、問題は二段構えだった。
- `https://172.16.1.59:4443/...` の IP直指定では `tcpProbe` は成功するが、`(-9984) X509 - Certificate verification failed` で TLS ハンドシェイクが失敗した。
- `https://mqtt.esplab.home.arpa:4443/...` の hostname 指定では ESP32 側DNS解決が失敗するが、fallback IP `172.16.1.59` へ接続しつつ、TLS検証ホスト名を `mqtt.esplab.home.arpa` のまま維持すると `Certificate verified.` となり OTA が成功した。
- 以上より、根本原因は「単純な到達性不足」ではなく、「ESP32のDNS不達」と「IP直指定時の証明書検証条件不一致」の組み合わせだった。

### 対策
- ESP32 OTA処理を `HTTPClient` 依存から外し、`WiFiClientSecure::connect(ip, port, tlsHostName, caCert, ...)` を用いる実装へ変更した。
- OTA URL が hostname の場合は、`WiFi.hostByName()` 失敗時に `SENSITIVE_MQTT_FALLBACK_IP` を利用して接続先IPを補完するようにした。
- TLS証明書検証は接続IPではなく hostname のまま維持し、`mqtt.esplab.home.arpa` 名義の証明書と一致させた。
- 実機再試験で `executeSingleOtaAttempt success.` と再起動後の `StartUp` status を確認し、OTA成功を確認した。
- OTA進捗通知は `write` を5%刻みに間引き、`done` は再起動前に待ち時間を確保して publish するよう調整した。
- LocalServer 側でも `start-up` status 受信時に `otaPhase=done` / `otaProgressPercent=100` / `otaDetail=rebooted after ota` へ収束させ、画面が古い `write` 状態で残らないようにした。
- [補足][2026-04-21] 現行実装では `SENSITIVE_MQTT_FALLBACK_IP` を DNS 補助として再利用可能に戻した。上記の fallback 記述は当時の経緯として残し、現行方針の正は `ネットワーク運用仕様書.md` と `MQTT_TLS環境構築まとめ.md` とする。
- [追記][2026-04-21] `IoT/LocalServer` の `test:connect` で MQTT 応答を確認し、`npm run test:7083 -- --iterations 1 --targetDeviceName IoT_04CEF94EB580` で OTA 成功を再確認した。  
  なお、今回の `waiting_device` 失敗は `IoT_F0D0F94EB580` と `IoT_04CEF94EB580` の対象個体名ずれが原因で、正しい個体名へ切り替え後は `workflow-signed-ota-1776740144679-26184` が `OK` になった。  
  理由: X509 解消の実機証跡を残す際に、対象機の取り違えが同じ失敗に見えないよう補足を追加するため。

### 再発防止
- [厳守] OTA用HTTPSポート追加時は、Node起動確認だけでなく「別端末（ESP32）」からの到達確認を必ず行う。
- [推奨] `コマンド仕様書.md` または `環境仕様書.md` に、OTA配布ポートのFirewall受信許可手順を明記する。
- [厳守] ESP32側で hostname URL を使う場合は、DNS不達時の fallback IP と TLS検証ホスト名を分離して扱う。理由: 「接続先IP」と「証明書照合名」は同一である必要がないため。
- [厳守][2026-04-21] 現行では DNS不達時の fallback IP を使わず、接続失敗をそのまま判定する。理由: FQDN 正経路を唯一の接続基準として固定し、暫定退避を残さないため。
- [禁止] 証明書検証を回避するために `setInsecure()` へ戻さない。理由: MQTT/OTAともに同一LAN内でもなりすまし検知を維持するため。

## 記録 #0004
- 見出し: 新ルータ運用開始後、ESP32 が NTP 同期待ちで MQTT 接続開始まで進まない
- 種類: 試験
- 分野: サーバー
- 状態: 解決済
- 試験番号: 7028
- 日時: 2026-03-08

### 症状
- `WiFi AP=172.17.1.1` `DNS=172.17.1.100` 環境で ESP32 書込み後、Wi-Fi 接続までは成功する。
- シリアルログで `applyWifiDnsConfiguration success. primary=172.17.1.100` と `wifi event handler: DNS re-applied after GOT_IP. dns1=172.17.1.100` は出る。
- しかし直後に `connectToWifiRouter DNS resolved setting. dns1=172.17.1.1` となり、`timeService::syncNow` がタイムアウトして `mainTaskEntry: skip mqtt connect until UTC sync for startup will registration.` のまま MQTT 接続へ進まない。

### 原因
- 暫定切り分けでは、CoreDNS 自体の名前解決機能は生きている。  
  - `nslookup mqtt.esplab.home.arpa 172.17.1.100` -> `172.17.1.100`
  - `nslookup ntp.esplab.home.arpa 172.17.1.100` -> `172.17.1.100`
  - `nslookup pool.ntp.org 172.17.1.100` -> 成功
- `Test-NetConnection -ComputerName 172.17.1.100 -Port 8883` も成功しているため、MQTT ポート到達性自体は成立している。
- 初回は `w32tm /stripchart /computer:ntp.esplab.home.arpa /samples:1 /dataonly` と `w32tm /stripchart /computer:172.17.1.100 /samples:1 /dataonly` が `0x80072746` で失敗したが、その後 `W32Time` 起動により応答成功へ変化した。
- 診断用に ESP32 の `timeServerUrl` を `172.17.1.100` 直指定へ変更すると、`timeService::syncNow succeeded.` と `NTP SYNC OK` を確認できた。
- よって主原因候補は以下のいずれか。
  - ESP32 の最終利用 DNS が `172.17.1.100` ではなく `172.17.1.1` へ戻っている
  - `ESP32` の `hostByName(mqtt.esplab.home.arpa)` と `SNTP(configTime)` で利用している解決経路/タイミングが異なる
  - `mqtt.esplab.home.arpa` に対する DNS 応答だけが ESP32 で取得できていない

### 対策
- [完了] `172.17.1.100` 上で UDP/123 の待受と `W32Time` 応答を確認する。
- [厳守] ESP32 の Wi-Fi 接続完了後に、実際に参照される DNS が `172.17.1.100` のままか再確認する。
- [厳守] `172.17.1.100:8883` で Mosquitto 等の MQTT ブローカー待受が継続している前提で、NTP サービスだけを個別に切り分ける。  
  理由: `8883/TCP` は到達しており、MQTT 側とNTP側を分離して調査できるため。
- [推奨] `mqtt.esplab.home.arpa` の A レコードが想定どおり `172.17.1.100` を返すか CoreDNS 設定を再確認する。  
  理由: 現行 `Corefile` では `172.17.1.100` を返す運用へ更新済みであり、クライアント側キャッシュや経路差異を切り分けるため。
- [推奨] 次段階の診断として、`mqtt.esplab.home.arpa` も一時的に `172.17.1.100` 直指定へ変更し、MQTT TLS 接続自体が成立するか確認する。  
  理由: MQTT 名解決問題と TLS/認証問題をさらに分離できるため。
- [完了] `MQTT` と `OTA` の接続順序を「IP設定ありなら先にIPで接続試行、TLS検証の正規名はFQDN維持」へ変更する。  
  理由: ローカル環境では DNS 不安定区間より先に IP で疎通を確立し、起動時間短縮と切り分け容易性を両立するため。
- [完了] `beta.8` 実機再試験で `connectToMqttBroker success. state=0` と `publishStatusNotice success.` を確認する。  
  理由: `IP優先 + FQDN保持` の併用仕様が実機で有効であることを確認できたため。

### 再発防止
- [厳守] 新ルータ切替時は「DNS Aレコード」「UDP/123」「ESP32実機ログ」を1セットで確認する。
- [禁止] NTP 未成立のまま MQTT 不達を DNS 単独の問題と断定しない。  
  理由: 現行起動シーケンスでは NTP 未同期だけで MQTT 処理が未実行になるため。

## 記録 #0008
- 見出し: ファイルログ有効化時に `/logs` 作成失敗と stack canary（`i2cTask` / `timeServerTask`）が再発する
- 種類: 試験
- 分野: 組み込み
- 状態: ペンディング（方針確定 / 実Broker適用待ち）
- 試験番号: 7048
- 日時: 2026-03-13

### 症状
- 7048/7049 実機検証でファイルログ有効化状態を作ると、起動直後に `open(): /littlefs/logs/<bootCount> does not exist, no permits for creation` が連続する。
- その後、`rotateLogFileIfNeeded rotated...` の出力直後に `Stack canary watchpoint triggered (i2cTask)` が発生し、再起動ループに入る。
- 失敗段階トレース追加後の再試験では、`LittleFS begin(): LittleFS Already Mounted` と `open(): /littlefs/logs/2026/0313/... no permits for creation` の直後に、`Stack canary watchpoint triggered (timeServerTask)` でも再起動した。

### 原因
- 調査中。現時点では「ファイルログ有効化時の `/logs` ディレクトリ作成/オープン失敗」と「i2cTask スタック余裕低下」が同時に起きていることのみ確認。
- `/logs` ディレクトリ判定強化修正（`log.cpp`）反映後の再試験でも、`open(): /littlefs/logs/... does not exist` の直後に `i2cTask` stack canary が再現したため、単純なディレクトリ/ファイル衝突だけでは説明できない。
- 追加再試験（最小1行固定 one-shot）では `open(): /littlefs/logs/2026/0313/... does not exist, no permits for creation` のみ再現し、`i2cTask` stack canary は未再現だった。  
  したがって、stack canary 側は「ファイルログ連続書込み時の負荷/呼出し頻度」が発火条件に含まれる可能性が高い。
- 失敗段階トレースでは `rotateLogFileIfNeeded active path does not exist yet` を確認。`LittleFS.exists(activeFileLogPath)` 呼出し時点で対象ファイル未作成なのは正常候補だが、同タイミングで `open(): ... no permits for creation` と stack canary が連鎖するため、`LittleFS` への同時アクセスやスタック破壊の影響を含めて再調査が必要。
- 単一ファイルログ書込みタスク化（PSRAM優先スタック）後は、`status` 200 回/620 回の連続投入で stack canary は未再現だったため、再起動要因には「複数タスクからの同時ファイルログ処理」が関与していた可能性が高い。

- 種類: 試験
- 分野: 組み込み
- 状態: ペンディング（原因確定）
- 試験番号: 7101
- 日時: 2026-04-05

### 症状
- `DEV-002(COM4)` へ `esp32s3_secure_final` を書込み後、起動ログで以下を確認。
  - `secureNvsInit::initializeSecureNvs: start. secureFinalBuild=1 ... plaintextFallbackAllowed=0`
  - `nvs_sec_provider.h is unavailable`
  - `plaintext fallback is prohibited by build policy`
- `setup` は `esp_ota_mark_app_invalid_rollback_and_reboot()` を呼び、起動継続せず rollback 経路へ遷移する。

### 原因
- 現行の PlatformIO/Arduino ビルド環境では、`nvs_sec_provider.h` を利用する secure provider が利用不能なため、`secure_final`（fallback禁止）条件を満たせない。
- その結果、`secure_final` は設計どおり fail-closed で停止し、通常起動へ進まない。
- [確認根拠][2026-04-05]
  - `python -m platformio system info` で `PlatformIO Core Directory: C:\\.platformio` を確認。
  - `C:\\.platformio\\packages\\framework-arduinoespressif32@3.20017.0` 配下を照合した結果、`nvs_sec_provider.h` は存在しない。
  - 同配下の `nvs_flash.h` は存在し、提供APIは `nvs_flash_read_security_cfg()` 系（旧経路）で、`nvs_sec_provider_register_hmac` / `nvs_flash_read_security_cfg_v2` は提供されていない。
  - 実機ログでも `secureProviderAvailable=0` と `nvs_sec_provider.h is unavailable` が一致しており、コード・実環境・実機ログの3点で整合した。

### 対策
- [厳守] 現環境では `esp32s3_secure_final` を `007-B` 進入条件に使わない。
- [重要] 実運用は `esp32s3_secure`（開発安全版）を維持し、`7101` の安定性ゲートを継続運用する。
- [重要] `secure_final` 評価は rollback 成否確認のみに限定し、出荷判定には使用しない。
- [関連] `esp32s3_secure_rescue` を回復専用として維持する（通常運用/出荷判定には不使用）。

### 案B PoC 結果（2026-04-07）
- [重要] `008-0045` の PoC により、案B（IDF寄せ）は **No-Go** と確定した。
- 根拠: 現行 `framework-arduinoespressif32@3.20017.0` は Arduino-ESP32 **v2.0.17**（ESP-IDF **v4.4.7** ベース）。`nvs_sec_provider` は ESP-IDF **v5.2 以降**の新 API であり、v4.4 には存在しない。
- Arduino v3.x（IDF v5.1+）へのメジャー更新は Wi-Fi/GPIO/SPI/I2C/UART/BLE 全 API に Breaking Change を含み、2〜4 週間級の工数で `007-C` 計画を大幅に阻害するため不採用。
- 次は案A（現行 PlatformIO/Arduino 寄せ）の評価へ移行する。
- 詳細: `最終セキュア化方式選定メモ.md` 7章。

### 再発防止
- [厳守] `secureFinalBuild=1` の実機適用は、事前に `nvs_sec_provider.h` 利用可否を確認したうえで実施する。
- [禁止] `secure_final` が fail-closed で停止した状態を「文鎮化」と短絡判定しない。まず rollback ログと `online` 復帰を確認する。
- [推奨] secure provider 可用性は `008-0040` と連動し、ビルド方式（PlatformIO/IDF）差分を明示管理する。

## 記録 #0026
- 見出し: `esp32s3_secure` / `esp32s3_secure_final` の ROM 使用率が 99.6% に達し、運用マージンが不足している
- 種類: デバッグ
- 分野: 組み込み
- 状態: ペンディング（原因切り分け済み）
- 試験番号: 7101
- 日時: 2026-04-05

### 症状
- `python -m platformio run -e esp32s3_secure_final -d IoT/ESP32` で `Flash: 99.6% (1305165 / 1310720 bytes)` を確認。
- `esp32s3_secure` も同様に `Flash: 99.6% (1305969 / 1310720 bytes)` であり、`secure_final` 固有の増分問題ではない。

### 原因
- [確定] 旧パーティション定義 `partitions/esp32s3_from_device_16MB_old.csv` の `app0/app1` は各 `0x140000`（1,310,720 bytes）で、アプリ上限が小さい。
- [確定] 上記パーティションCSVの最終アドレスは `0x400000` であり、16MB実機に対して **先頭4MB分しか使っていない**。そのため「16MB機なのに app 領域が極端に小さい」構成になっている。
- [重要] `board_build.flash_size=16MB` 設定でも、実際の上限は「パーティション定義」で決まり、現行は 2面OTAの各面がほぼ満杯。
- [切り分け] `xtensa-esp32s3-elf-size -A` で `.flash.text=934,439`、`.flash.rodata=279,824` が支配的。
- [切り分け] コンパイル成果物では `mqtt.cpp.o`、`maintenanceApServer.cpp.o`、`sensitiveData.cpp.o`、`ota.cpp.o`、`log.cpp.o`、`main.cpp.o` が大きい。
- [切り分け] `CORE_DEBUG_LEVEL=5` と詳細ログ文字列は、`.flash.rodata` 増加要因になりうる。

### 対策
- [第一候補] `007-B` 前に「16MB前提の新パーティション案」を設計し、`app` 面サイズ拡張可否を評価する。
- [候補メモ][2026-04-05] `app0=4MB` / `app1=4MB` / `NVS=100KB` / `filesystem=6MB` は概ね妥当な候補として保持する。ただし `otadata` / `coredump` / app offset整列を含めたCSV化検証を必須とする。
- [第二候補] ログ/機能の段階的削減（`secure_final` 用のログレベル最適化、未使用経路の compile-time 無効化）で binary を減量する。
- [厳守] パーティション変更は OTA 互換性・既存個体影響を伴うため、`DEV-002` でのみ先行検証し、`DEV-001` へは適用しない。
- [進捗][2026-04-06] `DEV-002(COM4)` へ候補案Aを実適用し、`app0=0x30000`、`app1=0x430000`、`spiffs=0x830000` の構成で `setup completed`、`Wi-Fi STA=172.17.1.200`、`NTP SYNC OK`、MQTT 接続・`status publish success` まで確認した。
- [重要][2026-04-06] 新CSV適用後に `python -m platformio run -e esp32s3_secure -t upload --upload-port COM4` をそのまま使うと、アプリが従来どおり `0x10000` に書かれ、`RTC_SW_SYS_RST` 連続の再起動ループになった。
- [対策確定][2026-04-06] `app0` が `0x30000` の間は、`platformio` の plain `upload` を主手順に使わず、`python -m esptool --chip esp32s3 --port COM4 write_flash 0x0 .pio/build/esp32s3_secure/bootloader.bin 0x8000 .pio/build/esp32s3_secure/partitions.bin 0x30000 .pio/build/esp32s3_secure/firmware.bin` と `uploadfs` を組み合わせる。
- [対策更新][2026-05-14] `IoT/ESP32/platformio.ini` の全ESP32 envに `board_upload.offset_address=0x30000` を明示し、`scripts/ensure_app0_upload_offset.py` を `extra_scripts` として追加した。これにより標準 `platformio -t upload` でも `ESP32_APP_OFFSET=0x30000` になり、設定が欠落・誤変更された場合はビルド/アップロード前に停止する。
- [確認][2026-05-14] `python -m platformio run -e esp32s3_secure` は成功し、`python -m platformio run -e esp32s3_secure -t envdump` で `ESP32_APP_OFFSET='0x30000'`、`INTEGRATION_EXTRA_DATA.application_offset='0x30000'` を確認した。
- [残課題][2026-04-06] 起動後ログに `esp_ota_ops: ota data invalid, no current app. Assuming factory` と `otaRollback::confirmCurrentAppIfNeeded failed` が残るため、`OTA` / `7101` へ進む前に boot label / otadata の扱いを追加確認する。
- [更新][2026-04-06] `LocalServer` の Rust MQTT transport で、受信常駐 `rx` 接続とは別に publish ごと `tx` 接続を新規作成していたため、起動直後の `Startup status request sent.` の直後に `mqttGateway rust disconnected` / `os error 10054` が連続し、`DEV-002` が `onlineState=offline` へ戻る事象を確認した。
- [対策確定][2026-04-06] `IoT/SecretCore/src/mqtt_transport.rs` を修正し、publish は受信常駐クライアントを共有する方式へ変更した。これにより `LocalServer` 起動直後の切断ループは解消し、`DEV-002` は `1.1.0-beta.33`、`1.1.0-beta.34` の OTA 2 回を連続 `OK` で通過できた。
- [残課題][2026-04-06] `AP` 側は未完了。`maintenance-reboot` 後に `ap/scan` では `AP-esp32lab-04CEF94EB580` を検出できるが、`Wi-Fi_lab` の `ap/connect` は timeout し、`7041:pipeline:strict` は `BLOCKED_AP_REACHABILITY` で停止した。現時点の差し止め要因は `AP` 到達経路のみである。
- [更新][2026-04-07] `LocalServer` の AP 接続アダプタを `wifiUsbInterfaceName=Wi-Fi_lab` に固定し、`maintenance-reboot` -> `ap/scan` -> `ap/connect` を再実行したところ、`AP-esp32lab-04CEF94EB580` 接続は `result=OK` で回復した。
- [更新][2026-04-07] `npm run test:7041:pipeline:strict` は `gateStatus=FULL_COMPLETED` となり、`#0026` で差し止めていた `AP` 到達ブロッカーは解消した。
- [補足][2026-04-07] `npm run test:7041:diag` は `Export-WlanEvents` のイベント取得処理で終了コード `NG` となったが、`7041-apdiag-20260407-093512` の診断一式（`wlan/ipconfig/route/arp/ping/curl`）は保存済み。`7041` 合否判定は strict gate の `FULL_COMPLETED` を正とする。

### 再発防止
- [厳守] 以後の機能追加時は `secure` / `secure_final` の size 計測を同日に記録し、`99%` 到達前に警告を上げる。
- [推奨] `最終セキュア化方式選定メモ.md` と連動し、方式選定（案B/A/C）に ROM マージン条件を含める。
- [禁止] ROM マージン不足のまま、不可逆工程の実運用判定へ進まない。

### 症状

- Wi-Fi_lab（TP-Link Realtek USB）：WLAN イベント id=11000 で `暗号化: AES-GCMP-128` によるアソシエーション試行 → id=8002（このネットワークを使用できません）で失敗。
- `netsh wlan show networks` では `AP-esp32lab-04CEF94EB580` が `Authentication: WPA2-Personal, Encryption: CCMP` として検出できており、SSID・電波強度に問題はなかった。

### 原因

**原因1（主因）: AP Wi-Fi パスワード不一致**
- `IoT/ESP32/shared/include/common.h` の `kMaintApPass` が **プレースホルダ `<AP_WIFI_PASSWORD>`** のままファームウェアに焼き込まれていた。
- PC 側 WLAN プロファイルは `LocalServer/.env` の `AP_WIFI_PASSWORD`（例: `pass-esp32`）を使用して生成されていたため、FW 実値と不一致となり WPA2 PSK 認証が失敗した。
- `configureEsp32CloudMode.ps1` の `$MAINT_PASS = 'esp32m1732'` は Web API ログイン用であり、AP Wi-Fi パスワードとは別物。

**原因2（Wi-Fi_lab 固有）: Realtek アダプタによる GCMP 選択**
- Wi-Fi_lab（TP-Link Wireless USB Adapter、Realtek RTL8192EU ドライバ `rtwlanu.sys`）が AES-GCMP-128 でアソシエーションを試みた。
- Arduino-ESP32 2.0.17 の pre-built `libesp_wifi.a`（IDF 4.4.x コンパイル済み）が RSN IE に GCMP をアドバタイズするため、クライアントが GCMP を選択する。
- ESP32 IDF 4.4 の softAP は GCMP 4-way handshake を完了できないため接続失敗となる。

### 対策

**対策1（根本・原因1解消）: WLAN プロファイルを FW 実値に合わせる**
- WLAN プロファイルのパスワードを ESP32 FW の `kMaintApPass` 実値に変更することで Intel Wi-Fi / Wi-Fi_lab ともに接続可。
- FW ビルド後に `firmware.bin` 内を文字列検索し、`<AP_WIFI_PASSWORD>` プレースホルダが残っていないことを AP 試験前チェックとして実施する（`#0040` 対策参照）。

**対策2（FW 修正・原因2解消）: pairwise_cipher = CCMP 強制**
- `IoT/ESP32/src/main.cpp` の `startMaintenanceApModeAndHold()` 内、`WiFi.softAP()` 直後に以下を追加（2026-05-20 実施済み）：
  ```cpp
  wifi_config_t apCfg = {};
  esp_wifi_get_config(WIFI_IF_AP, &apCfg);
  apCfg.ap.pairwise_cipher = WIFI_CIPHER_TYPE_CCMP;
  esp_wifi_set_config(WIFI_IF_AP, &apCfg);
  ```
- これにより beacon の primary pairwise cipher が CCMP になり、Wi-Fi_lab の GCMP 選択を抑制できる。

## 記録 #0046
- 見出し: ESP32 NVS の k-device 消失（起動後 MQTT 接続不能）
- 種類: 試験
- 分野: 組み込み
- 状態: **復旧済**（根本原因は未特定、`todo.md` `020-0016` で継続調査）
- 試験番号: 012-0008
- 日時: 2026-05-20

### 症状
- ESP32 起動後にシリアルログで `[ERROR] loadKDeviceBytes failed. key size must be 32. actual=0` が出力され、MQTT 接続が失敗する。
- `012-0008` クラウド統合試験の着手時に発生。

### 原因

**根本原因: 未特定（`todo.md` `020-0016` で継続調査）**

NVS 領域（`0x9000`）の k-device が消失した。発生メカニズムとして以下が考えられるが、特定には至っていない：
1. **開発中の全消去操作**：`esptool.py erase_flash` 等によるチップ全消去が実施された可能性。意図的・偶発的どちらもあり得る。
2. **`secureNvsInit.cpp` の `nvs_flash_erase()` 自動発火**：`nvs_flash_init()` が `ESP_ERR_NVS_NEW_VERSION_FOUND` または `ESP_ERR_NVS_NO_FREE_PAGES` を返した際に NVS 全消去が走る実装（[secureNvsInit.cpp:145](src/secureNvsInit.cpp#L145) / [secureNvsInit.cpp:282](src/secureNvsInit.cpp#L282)）。フレームワーク版（`arduinoespressif32@3.20017.0`）固定運用では通常発生しないが、例外的なパーティション整合崩れや NVS 満杯時に発火する。
3. **パーティション CSV アドレス設定誤り**：`platformio.ini` の `board_build.partitions = partitions/esp32s3_16MB_current.csv` は確認済みで NVS（`0x9000`）と LittleFS（`0x830000`）は重複しない。現状設定に起因する可能性は低い。

なお、`uploadfs`（LittleFS `0x830000` への書き込み）は NVS 領域を直接触らないため直接原因ではない。また OTA による通常のファームウェア更新（`app0`/`app1` 領域）でも NVS は消去されない。

### 対策（復旧手順）

1. `IoT/LocalServer/scripts/createSensitiveDataJsonForRecovery.cjs` で k-device を復旧用 JSON として書き出す：
   ```
   cd IoT/LocalServer && nvm use 22
   node scripts/createSensitiveDataJsonForRecovery.cjs IoT_04CEF94EB580
   ```
2. ESP32 を USB 接続し LittleFS にアップロードする（SecretCore / LocalServer は停止させておく）：
   ```
   cd IoT/ESP32
   pio run -e esp32s3_secure --target uploadfs --upload-port COM4
   ```
3. ESP32 を再起動し、シリアルログで `recovered keyDevice from legacy LittleFS` を確認する。
4. 再度 `uploadfs` で `sensitiveData.json` なしの状態に戻す（クリーンアップ）。
5. 復旧完了後、`IoT/ESP32/data/sensitiveData.json` が残っていないことを確認する（`ESP32/.gitignore` で除外済み）。

### 再発防止
- [推奨] ファームウェアを新規ビルド・書込みする前に `createSensitiveDataJsonForRecovery.cjs` を実行して k-device をバックアップしておく（特に開発初期・実機セットアップ直後）。
- [参考] `secureNvsInit.cpp` の `nvs_flash_erase()` 発火時はシリアルに `[W] plaintext NVS needs erase` または `[W] secure NVS partition needs erase` が出力される。NVS 消失が発生した際はこのログを最初に確認する。

## 記録 #0047
- 見出し: ESP32 cloud mode で `pingBrokerHost` がローカル broker IP を強制使用しクラウド X.509 検証失敗
- 種類: 設計バグ・コード
- 分野: 組み込み（ESP32 / MQTT）
- 状態: **修正済**（`mqtt.cpp` 修正、build SUCCESS / フラッシュ済）
- 試験番号: 012-0008（7200 前段）
- 日時: 2026-05-21

### 症状
- ESP32 を `brokerMode=cloud` に設定し AWS IoT Core への接続を試みると、TLS handshake で `(-9984) X509 - Certificate verification failed` が発生して接続できない。
- シリアルログ: `pingBrokerHost: configured IP will be used before DNS. brokerHost=...amazonaws.com configuredIp=172.17.1.100` の後に `mqttClient.setServer uses resolved IP. host=...amazonaws.com ip=172.17.1.100 port=8883` が出る。

### 原因
- `IoT/ESP32/src/MQTT/mqtt.cpp` の `pingBrokerHost`（ローカルモード向けの DNS 短絡）が `SENSITIVE_MQTT_FALLBACK_IP`（=ローカル Mosquitto IP `172.17.1.100`）を broker モードに依存せず無条件で適用していた。クラウドモードで AWS の FQDN を指定しても、解決結果がローカル broker IP に書き換えられ、その IP に対する TLS が AWS の証明書では検証通らず失敗していた。
- 加えて、`applyWifiDnsConfiguration` は `SENSITIVE_WIFI_DNS_PRIMARY_OCTET*` の固定値（CoreDNS）を設定する設計で、cloud mode に必要な外部 FQDN 解決を考慮していなかった。

### 対策
1. `mqtt.cpp:pingBrokerHost` を修正し、`mqttBrokerMode == "cloud"` の場合は `SENSITIVE_MQTT_FALLBACK_IP` バイパスをスキップし `WiFi.hostByName` のみを使用するよう分岐を追加（local mode は既存挙動を完全維持）。
2. `mqtt.cpp:connectToMqttBroker` に cloud mode 専用の DNS 再設定ブロックを追加。`primary=172.17.1.100 (CoreDNS), secondary=8.8.8.8` を `WiFi.config(INADDR_NONE, INADDR_NONE, INADDR_NONE, ...)` で適用し、外部 FQDN 解決の冗長性を確保（local mode では本処理を行わない）。
3. これによりクラウドモードで `mqttHost` (AWS FQDN) を `setServer` に正しく渡せるようになり、ローカル broker IP への誤接続は解消した。

### 再発防止
- [厳守] 「configured IP fallback」のような DNS 短絡ロジックを書く場合は、必ず broker モード（local / cloud）を分岐条件に含める。外部 FQDN に対してローカル fallback IP を適用してはならない。
- [厳守] cloud mode の TLS は SNI 必須。`setTlsValidationContext(hostname, caCert)` で hostname を明示し、`setServer(IPAddress, port)` でも SNI が外れないことを確認する。
- [推奨] 新規の cloud / local 共通コードは「broker モードに依存する分岐」をコメントで明示する。
- [参照] `todo.md` `012-0008` / `010-0011`（CoreDNS forward 設計） / 関連: `#0048`（後述：DNS 経路問題）

## 記録 #0048
- 見出し: ESP32 → DNS 経路不通（`#0047` 修正後も `hostByName` 失敗で `012-0008` 7200 ブロック）
- 種類: ネットワークインフラ
- 分野: ネットワーク・運用
- 状態: **未解決**（調査中、`012-0008` 7200 着手前に解消が必要）
- 試験番号: 012-0008（7200 前段）
- 日時: 2026-05-21

### 症状
- `#0047` 修正後、ESP32 cloud mode で DNS 設定が `dns1=172.17.1.100 dns2=8.8.8.8` と正しく適用されているにも関わらず、`hostByName(): DNS Failed for a18obaz8zsc0rk-ats.iot.ap-northeast-1.amazonaws.com` で約 8 秒タイムアウト後に失敗する。
- 同じ FQDN を **PC からは** `nslookup ... 172.17.1.100` も `nslookup ... 8.8.8.8` も成功（35.72.221.248 解決）。

### 原因（仮説）
1. **AP のクライアント分離**：ESP32 が接続する物理 AP（`AP-IoTESP32Test`）が無線クライアントから 172.17.1.x の他ホスト（特に PC の 172.17.1.100）への通信を遮断している可能性。
2. **CoreDNS の bind / ACL**：PC 上の CoreDNS が `イーサネット 2` インタフェース（172.17.1.100）に bind しているが、外部 IP（ESP32 の 172.17.1.200）からのクエリを明示的に許可していない可能性。
3. **PC のホストファイアウォール**：DNS 用 53 ポートは Allow ルールあり（`DNS_UDP53` / `DNS_TCP53`）だが、Profile=Any でも実効的にブロックされているケース。
4. **物理ルータ（172.17.1.1）の NAT / forwarding**：外部 DNS（8.8.8.8）へ ESP32 の UDP 53 を forward していない可能性。

### 調査ポイント（次セッション）
- PC の `イーサネット 2` 上に CoreDNS 設定ファイル（`Corefile` 等）の場所を特定し、bind / ACL（`hosts`, `acl` plugin）を確認する。
- ESP32 から PC への ICMP / TCP 80 等が通るか別経路で確認（実機 LCD or LocalServer 経由）。`#0047` 修正前は ESP32 → 172.17.1.100:8883 (Mosquitto) は到達できていた（`pingBrokerHost success`）ため、UDP 53 のみブロックの可能性も。
- 物理 AP / ルータの管理画面で「クライアント分離」「DNS proxy / forwarding」設定を確認。
- 代替案として、ESP32 cloud mode で `connectToMqttBroker` の前段に「事前 DNS テスト → 失敗時はローカル UDP DNS スタックで再試行 or 既知 IP（CloudWatch リソース等で取得した AWS 固定 IP）にハードコード」する案。ただし AWS の IoT Core エンドポイント IP は変動するためハードコードは非推奨。

### 対策候補
- **本命**: CoreDNS の bind / ACL を見直し、ESP32 を含む 172.17.1.0/16 全体から forward 可能にする（todo `010-0011` / `010-0012` の本格対応）。
- **暫定**: 物理 AP のクライアント分離を解除する。
- **代替**: PC 上に簡易 DNS proxy を Wi-Fi_lab 側に追加し、ESP32 専用 DNS とする。

### 続報（2026-05-21 続⁴・🎉012-0008 大部分クリア + brokerMode 切替バグ修正）
